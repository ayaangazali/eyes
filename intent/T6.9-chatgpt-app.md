## Why
ChatGPT apps and claude.ai custom connectors need OAuth (static bearer keys are not accepted there) and render rich results only through MCP Apps UI resources. Eyes answers are visual (a photo plus three checks), so plain JSON undersells them.

## What

Historical implementation notes: the five-tool metadata list and `${public_api_url}/mcp` Claude hash below describe the original API-host setup, not the current tool count or dedicated-host origin. Use the current status above and [CONNECT.md](../docs/CONNECT.md) for the 13-tool server and host-specific metadata. The original design and verification evidence are retained.

- One widget resource `ui://eyes/card.html` (`text/html;profile=mcp-app`): the packages/ui tokens, components and icons inlined, plus a small vanilla script that speaks the MCP Apps bridge (`ui/initialize`, tool-input, tool-result, host-context-changed, size-changed) with a `window.openai` fallback. It renders a quote card, a live task card (status steps, photo in the viewfinder frame, answer, GPS/fresh/vision checks, cost) or a balance card. Light and dark follow the host theme.
- quote_task, ask_eyes, await_answer, get_task and get_balance carry `openai/outputTemplate` plus invoking/invoked labels; a `mcp:tools/list` middleware adds `_meta.ui.resourceUri` (mcp-use strips it from tools without an mcp-use React view). Photo CSP allows the InsForge storage host and its CDN. For Claude (client name or user agent contains "claude"), the resource read result carries `_meta.ui.domain` = the first 32 hex characters of SHA-256 of `${public_api_url}/mcp` plus `.claudemcpcontent.com` (Claude's documented rule). Other hosts get no `ui.domain`, because a wrong value makes Claude refuse to render; ChatGPT gets `openai/widgetDomain` and `openai/widgetPrefersBorder`.
- Stateless OAuth 2.1 (`EYES_OAUTH_SECRET`): protected-resource and authorization-server metadata, DCR with an AES-GCM sealed client_id, a login page that takes an existing key or creates one through the signup service (same per-IP budget as `/v1/signup`), sealed 5-minute codes, PKCE S256 only. The access token is the Eyes API key, so the `/mcp` bearer check and existing agents are unchanged. 401 responses carry `WWW-Authenticate: Bearer resource_metadata=...`.

- Domain split: optional `EYES_PUBLIC_MCP_URL=https://mcp.eyes.pictures/mcp` selects the dedicated OAuth issuer, resource and card origin on that host. Legacy API connectors retain their API issuer and card domain. The existing HTTP adapter authenticates forwarded hosts with `EDGE_SECRET`; REST, upload, webhook and worker link configuration remains `EYES_PUBLIC_API_URL`. Both domains use the existing Worker and Manufact process; `ORIGIN` is unchanged. Code configuration does not migrate third-party connectors; the owner's two web connectors were migrated separately.
- No workers nearby: the quote card shows a warning "No one nearby" badge, not green "Can ask" (red "Can't ask" stays for refusals). Over MCP only, ask_eyes answers `no_workers_nearby` as a normal result `{status: "not_sent", reason: "no_workers_nearby", charged_usd: 0, message, fix}`, so hosts do not show the call as failed (nothing was created or charged); the widget renders it as a "Not sent" card with the place. REST `POST /v1/tasks` keeps the 409 error. The MCP ask_eyes outputSchema is one object with `status` "dispatched" or "not_sent" (MCP outputSchema roots must be type object), and the description says what not_sent means.

## Decisions & alternatives rejected
- mcp-use views (React + Vite build) rejected: a build pipeline for five static cards. mcp-use `oauthProxy` rejected: needs an upstream IdP plus persistent storage (a DB migration).
- No CIMD: ChatGPT and Claude both do DCR; CIMD means fetching client-chosen URLs.
- Known ceiling: no token expiry or refresh, revoke by rotating the key; a code is replayable within 5 minutes by the same client with the same verifier.


### Explicit task confirmation

Interactive `ask_eyes` returns `confirmation_required` with the normalized input, intent key and free quote. It never invokes the dispatch service. The card calls native app-only `confirm_ask` after the user confirms. The existing transaction enforces same-agent/same-key idempotency; no approval table or question/time-window deduplication is added. REST, email, CLI and non-UI MCP retain direct dispatch. Detection uses negotiated MCP Apps support first, then only known versioned ChatGPT/Claude browser identities, not a generic Claude-name match.
Interactive invocation labels describe draft preparation and confirmation review, not a posted task. Non-UI `ask_eyes` and app-only `confirm_ask` retain their dispatch labels.
Interactive discovery uses preparation-specific input descriptions and an output schema containing only `confirmation_required`, the preserved request fields and quote data. It cannot advertise task IDs, escrow or dispatch results for a draft. Non-UI discovery and app-only confirmation keep their existing dispatch contracts.
`confirm_ask` is callable by the existing card but does not render its own widget. It has no output-template or resource binding; the card renders its returned result. Its app-only/private visibility and mutating/idempotent annotations are unchanged.
Server guidance and `await_answer` describe the existing read-only wait: only a dispatched task ID is valid, responses can contain no answer or photo, and stored settlement status is distinct from verification flags. Waiting does not dispatch, pay, refund or keep a background subscription alive. Error guidance cannot authorize a new charge or bypass card confirmation.
MCP initialization omits optional shared instructions. Tool descriptions and next steps carry the workflow; both model-visible `ask_eyes` variants retain bounded error-repair authorization, and sandbox descriptions retain their simulation notice.

The card preserves dirty fields, its intent key and frozen submitted parameters across notifications and retries. A new Ask Again creates a new key and requires a fresh confirmation. Supported model-context updates report the created task rather than asking the model to dispatch it again. Host visibility is a conforming-client boundary, not authenticated evidence of a human click in arbitrary clients.
Visible pending-task cards refresh through read-only `get_task` every five seconds, with serialized reads and stale-view guards. Pending status remains authoritative even with a partial answer. Hidden cards pause; leaving pending states, teardown and read errors stop polling. Manual Refresh can recover from a read error. This adds no paid calls or background host subscription.

The resource URI changes to `ui://eyes/confirmation-card.html` for the breaking paid-call contract. Refresh/rescan tool metadata and start a new quote; already rendered cards are not updated. Old interactive card calls remain read-only. Quote data never bypasses final safety/spend validation. Ask Again preserves the stored deadline and photo requirement, but never reuses a consumed classifier approval for a new intent.

### Independent checks at one place

The same location is not request identity. **New check here** creates a UUIDv7 request intent synchronously, preserves the place and non-evidence defaults, clears the question/evidence and obtains a free quote. **Repeat previous question** copies text only. The existing private confirmation creates the Task; identical retries retain the original key and frozen payload. Generated fallback draft keys and disputed-card Ask again keys also use UUIDv7. Caller-supplied keys remain opaque strings and are never rewritten; Task, Submission and ledger identifiers do not change.

Widget state is a versioned, bounded set of 20 recent intent/Task records, not a new history store. **Resume pending** and **View previous** select explicit records. The existing `list_tasks` read can fill the bounded recent list; no cursor contract, schema migration or optional upload/multi-photo work is included. Selected cached Tasks are re-read under current authorization before showing evidence.

Activation and result merging belong to the explicit intent/Task in both host bridges. Fresh identified host drafts replace unrelated saved completion; same-intent stale drafts still cannot downgrade a Task. Async confirmations preserve their original record through navigation; quote/read/error/finally callbacks cannot mutate a newer selection. An unresolved confirmation is never evicted. A separate check requires a warning while its outcome is unknown; unavailable persistence blocks switching instead of discarding a potentially paid request. A later `not_sent` response during an unknown retry is not proof that the original attempt did not commit: the card retains the frozen key/payload and unresolved warning instead of claiming $0 charged.

The UUIDv7 generator is a small standalone browser function: 16 cryptographically random bytes, six big-endian timestamp bytes from `Date.now()` using division (no 32-bit timestamp truncation), version 7 and RFC variant bits. No framework, dependency, new paid tool or database migration is added. Current server guidance distinguishes reading/resuming an existing Task from requesting a fresh observation, including identical place/question.

This cutover uses canonical `ui://eyes/scene-card-v2.html` and a single `{version: 2, active, records}` envelope, with a one-way reader for prior saved state. The former confirmation resource is not registered as an alias. Publishing must refresh host tool metadata and render a new card; cached messages keep their old script. `confirm_ask` stays private/call-only. The dated deployment evidence and earlier resource names above remain historical, not a claim that this changeset has shipped.
