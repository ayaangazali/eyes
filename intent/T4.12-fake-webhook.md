## Why
With `STRIPE_SECRET_KEY` unset, payments use `fakePayments`, whose `parseWebhook` accepts the public constant `FAKE_STRIPE_SIGNATURE` ("fake-signature") and returns the request JSON as the event. The live deploy runs that way today and will keep doing so while Inkbox goes live first. So anyone could `POST /webhooks/stripe` with that header and credit any agent's balance (a fresh `ref` each time beats the `(type, stripe_ref)` replay guard), mark any worker onboarded, and after PR #53 make Eyes email an agent's owner link to an address they choose. Found by the main-branch security sweep and the T4.10 verifier (scratchpad `verdicts/SEC-main-sweep.md` finding 1, `verdicts/T4.10-PR53.md` deploy note).
## What
- `createServer` answers every `POST /webhooks/stripe` with the standard JSON 404 when payments are fake (`liveProviders(env).payments` is false) and `EYES_FAKE_WEBHOOKS` is not `"1"`. The handler is registered before `stripeRoutes`, so the body is never read or parsed and the service is never called.
- `EYES_FAKE_WEBHOOKS` is a local-test-only opt-in. It is listed empty (off) in `.env.example`; no committed runner sets it, because no e2e spec, eval or script sends a fake Stripe webhook (checked: `e2e/`, `apps/web/worker/e2e/`, `playwright.config.ts`, `evals/ax/run.ts`, `scripts/`, `cli/`). The one in-process test that does (`server.test.ts` "mounts the Stripe routes at the root") now sets it.
- The other Stripe routes (`/topup/*`, `/w/connect/*`) and the real Stripe path are unchanged: when payments are live the guard is not mounted and `stripeRoutes` verifies with `STRIPE_WEBHOOK_SECRET` / `STRIPE_CONNECT_WEBHOOK_SECRET` as before.
## Decisions & alternatives rejected
- 404 over 401: in fake-payments mode no Stripe account is connected, so the route has no legitimate sender and is simply not served. A 404 is the same "Unknown route." body as any unmounted path (smoke-live accepts any 4xx), and it does not suggest that some signature or credential would be accepted. A 401 would invite signature guessing and mislead an operator into checking a webhook secret that is not in use.
- Guard in `createServer` over `stripeRoutes` or `fakePayments`: `liveProviders(env)` in `server.ts` is the single place that decides live vs fake (`main.ts` builds the providers from it), so the guard uses the same decision. `stripeRoutes` cannot tell a fake adapter from a real one, and `packages/core/src/fakes.ts` is a frozen contract that the unit and contract tests rely on.
- Opt-in flag over refusing to boot with `EYES_PROVIDERS=live` and no Stripe key (sweep fix (a)): the deploy intentionally runs fake payments until Stripe keys land (PLAN §4 order), and a fake-mode server with no `EYES_PROVIDERS=live` would still expose the faucet. Closing the route closes both.
- Inkbox and Primitive webhooks need no change: `inkboxRoutes` returns 401 unless `INKBOX_WEBHOOK_SIGNING_KEY` is non-empty and the Svix HMAC verifies (`packages/comms/src/inkbox.ts` `authentic`), and `primitiveRoutes` verifies the HMAC against `PRIMITIVE_WEBHOOK_SECRET` and fails closed when it is unset. Neither depends on whether a provider is fake, and both fail-closed cases are already tested (`inkbox.test.ts` "rejects everything when the signing key is ...", `primitive.test.ts` "fails closed when PRIMITIVE_WEBHOOK_SECRET is not set").
## Assumptions
- Hono runs routes in registration order and a handler that returns without calling `next` ends the chain, so the guard shadows the `stripeRoutes` POST handler. Proven by the test (404, no credit) rather than assumed.
## Verification
- `apps/mcp/src/server.test.ts` "refuses a fake-signed Stripe webhook while payments are fake unless EYES_FAKE_WEBHOOKS=1": a `topup.completed` for 100,000 cents signed `fake-signature` gets 404 "Unknown route." with env `{}`, `{EYES_PROVIDERS: live}` (no Stripe key) and `{STRIPE_SECRET_KEY}` (not live), and `creditTopup` is never called; `/topup/done` still serves 200; with `EYES_FAKE_WEBHOOKS=1`, and with live payments (`EYES_PROVIDERS=live` plus `STRIPE_SECRET_KEY`), the request reaches the parser and credits (200).
- Reverted to prove it: with `apps/mcp/src/server.ts` from origin/main the new test fails (`expected 200 to be 404`); restored after.
- `pnpm verify:fast`: pass (biome 98 files no fixes, typecheck, unit 17 files / 492 tests, contract 11, safety 139, intent check), before and after merging origin/main.
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t412 pnpm test:integration` on a fresh, migrated `eyes_t412` after merging origin/main (PR #53 included): 6 files, 78 passed.
- `CI=1 DATABASE_URL=.../eyes_t412 pnpm test:e2e` locally (ports 4173, 4174, 3399 free): 25 passed. No spec sends a Stripe webhook, so none needed the flag.
- Verifier: security **PASS** ([verdicts/T4.12-PR56.md](verdicts/T4.12-PR56.md)): 26 path/method/content-type variants of a forged fake-signature top-up all 404 with the balance unchanged; with the flag, exactly the same 12 reach the parser; the real Stripe path is unchanged and the flag cannot re-enable the fake parser when payments are live.

## Known gaps
- The guard keys on env, as `main.ts` does. A test harness that passes live env with fake providers still accepts the fake signature; no deployed process can reach that state.
- `.env.example` has no comment lines, so "local-test only" is recorded here and in the PR body, not next to the variable.
