## Why
Every transport (MCP, REST, worker web, email, CLI) calls `EyesService`; this is the implementation. Money moves must be atomic and retry-safe, so every state transition is one plpgsql function and the engine only orchestrates providers around those calls.

## What
- `002_engine.sql`: `eyes_*` functions for signup, top-up, post task (idempotency check, no-workers check, daily cap, balance debit, task, escrow row and offers in one call), claim, submit plus settle, record payout, cancel, dispute, expire, worker upsert and opt-in, reads. Business time is `p_now`. Errors are `raise exception 'eyes:<code> <json context>'`. Execute is revoked from PUBLIC, `anon`, `authenticated`.
- `@eyes/db`: `createRpc(DbConfig)` (postgres: `select to_jsonb(r) from fn(p_a => $1, ...) r`; insforge: `POST {base_url}/api/database/rpc/{fn}`), maps `eyes:` errors to `EyesError`; `createInsforgeStorage(env)`.
- `@eyes/engine`: `createEyesService` implementing every `EyesService` method; offers carry `task_type` (ADR-005).

## Decisions & alternatives rejected
- Rows cross both transports as JSON (`to_jsonb` mirrors PostgREST), so bigint, timestamps and composites look the same in CI and on InsForge. Single-column `returns table` functions are avoided because both serialize them as bare scalars.
- Offers are inserted inside `eyes_post_task`, and the idempotency check runs before the no-workers, cap and balance checks, so a retry always returns the original task without re-texting anyone. Card order kept everything else.
- Daily cap is enforced inside `eyes_post_task` under the agent row lock (atomic) instead of a racy engine pre-check; it counts escrow minus refunds for tasks created since UTC midnight of `p_now`.
- Submission and settlement are one function (`claimed -> verified` with release and fee rows, or `needs_review`), because the frozen `submissions` row needs verification results; no window leaves escrow orphaned in `submitted`.
- Race-safe claim: conditional `update ... where status = 'dispatched'`; a worker who already holds the claim gets the same link (deterministic token); a later YES on a task someone else holds gets `sendAlreadyClaimed`.
- `eyes_expire_overdue` takes a transaction advisory lock so overlapping cron runs cannot deadlock; refunds use the ledger's unique `(task_id, type)`.
- `eyes_record_payout` targets `on conflict (task_id, type)` only, so a reused transfer id fails loudly instead of marking the task paid with no payout row (found by rerunning the suite on a dirty database).
- START sets `available = true` as well as `opted_in`, else a worker who sent STOP then START could never be dispatched again. Re-joining keeps `opted_in`.
- Payout failure after verification is logged and leaves the task `verified` with a truthful worker message, instead of failing a capture that already succeeded.
- Photos go to bucket `photos` (task card) although the vendor note planned `captures`.

## Assumptions
UNVERIFIED on InsForge (docs/vendor/insforge.md): RPC returns a JSON array of rows with composite columns nested, accepts a JSON array for `uuid[]`, and reports `raise exception` text in the error body's `message`; the admin key's role owns or can execute the `eyes_*` functions (they are SECURITY INVOKER and revoked from PUBLIC, so a non-owner admin role needs an explicit grant); `createAdminClient({baseUrl, apiKey})` uploads to a public bucket `photos` created at deploy and returns a public `data.url`.

## Verification
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t12 pnpm test:integration`: 11 passed (7 engine, 4 schema), three consecutive runs on the same database.
- Golden path forces the claim race: a test transaction row-locks the task until both claim calls are blocked on it. Removing `and status = 'dispatched'` from `eyes_claim` makes the test fail with two capture links.
- Money tests: insufficient balance, idempotent retry, idempotency conflict, cancel once, overlapping expiry refunds once, no_workers_nearby and unsafe_task charge nothing, daily cap with refunds freeing it.

- `pnpm verify:fast` passes.

## Known gaps
- No retry for `verified` tasks whose payout failed or whose worker had no Stripe account; `markWorkerOnboarded` is a no-op. A dispute between settle and transfer cannot stop that transfer.
- `eyes_nearby_workers` scans all available workers (no geo index); fine for a demo pool.
- `owner_email` from signup is not stored (no column). Top-up success and cancel URLs (`/topup/success`, `/topup/cancel`) are not in `HTTP_ROUTES` yet (T2.1).
- `fakePayments` transfer ids restart at `tr_fake_1` per instance, so two test files that pay out against one database collide on `ledger_stripe_ref`; the engine test suffixes ids. Proposed core fix: include a random part in fake transfer ids.
