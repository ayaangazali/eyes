## Why
Every transport (MCP, REST, worker web, email, CLI) calls `EyesService`; this is the implementation. Money moves must be atomic and retry-safe, so every state transition is one plpgsql function and the engine only orchestrates providers around those calls.

## What
- `002_engine.sql`: `eyes_*` functions for signup, top-up, post task (idempotency check, daily cap, no-workers check, balance debit, task, escrow row and offers in one call), claim, submit plus settle, record payout, pending payouts, cancel, dispute, expire, worker join and opt-in, reads. Business time is `p_now`. Errors are `raise exception 'eyes:<code> <json context>'`. RLS is enabled on all six tables with no policies; table privileges and function EXECUTE are revoked from `anon` and `authenticated` (and EXECUTE from PUBLIC).
- `@eyes/db`: `createRpc(DbConfig)` (postgres: `select to_jsonb(r) from fn(p_a => $1, ...) r`; insforge: `POST {base_url}/api/database/rpc/{fn}`), maps `eyes:` errors to `EyesError`; `createInsforgeStorage(env)`.
- `@eyes/engine`: `createEyesService` implementing every `EyesService` method; offers carry `task_type` (ADR-005).

## Decisions & alternatives rejected
- Rows cross both transports as JSON (`to_jsonb` mirrors PostgREST), so bigint, timestamps and composites look the same in CI and on InsForge. Single-column `returns table` functions are avoided because both serialize them as bare scalars.
- In `eyes_post_task` the idempotency check runs first, so a retry returns the original task without re-texting anyone; then daily cap, then no-workers, then balance, all under the agent row lock. The cap counts escrow minus refunds for tasks created since UTC midnight of `p_now`.
- Submission and settlement are one function (`claimed -> verified` with release and fee rows, or `needs_review`), because the frozen `submissions` row needs verification results; escrow is never orphaned in `submitted`.
- Race-safe claim: conditional `update ... where status = 'dispatched'`; a worker who already holds the claim gets the same link; a later YES on a task someone else holds gets `sendAlreadyClaimed`.
- `eyes_expire_overdue` takes a transaction advisory lock so overlapping cron runs cannot deadlock; refunds rely on the ledger's unique `(task_id, type)`.
- `eyes_record_payout` targets `on conflict (task_id, type)` only, so a reused transfer id fails loudly; it returns a row only to the call that moved `verified -> paid`, so overlapping payouts text the worker once. Capture and `markWorkerOnboarded` share one payout path (`payout:{task_id}`).
- Worker takeover (security review): `joinWorker` always returns `connect_url: null` and never modifies an opted-in worker (same response either way, so it does not reveal whether a phone exists). The payout link is texted after START, which proves phone ownership. `c:` links expire after 7 days and are minted per send.
- START sets `available = true` as well as `opted_in`; STOP from an unknown phone gets no reply.
- Redirects: top-up `{public_api_url}/topup/done` and `/topup/cancel`; onboarding refresh `{public_api_url}/w/connect/{same token}`, return `{public_api_url}/w/connect/done`. Bucket `photos`.
- Payout failure after verification is logged and leaves the task `verified` (payout pending) with a message pointing at payout setup, instead of failing a capture that already succeeded.

## Assumptions
UNVERIFIED on InsForge (docs/vendor/insforge.md): tables are exposed at `/api/database/records/<table>` and the anon key maps to role `anon` ("Row-level security model"); per the security review InsForge grants ALL on public tables to `anon` and `authenticated`, hence RLS plus revokes. The admin key's role must own the tables or have BYPASSRLS, and must own or be granted EXECUTE on the SECURITY INVOKER `eyes_*` functions. RPC returns a JSON array with composite columns nested, accepts a JSON array for `uuid[]`, and puts the `raise exception` text in the error body's `message`. `createAdminClient({baseUrl, apiKey})` uploads to a public bucket `photos` created at deploy and returns a public `data.url`.

## Verification
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t12 pnpm test:integration`: 13 passed (9 engine, 4 schema), repeated runs on a fresh and a reused database.
- Claim race is forced: a test transaction row-locks the task until both claim calls block on it; removing `and status = 'dispatched'` fails the test with two capture links.
- Money: insufficient balance, idempotent retry, idempotency conflict, cancel once, overlapping expiry refunds once, no_workers_nearby and unsafe_task charge nothing, daily cap with refunds freeing it.
- Onboarding: capture without Stripe stays `verified`; two overlapping `markWorkerOnboarded` calls pay once. Making it a no-op fails the test.
- Takeover: a second join cannot change an opted-in worker, `connect_url` is null, START texts a `/w/connect/` link. Dropping `where not workers.opted_in` fails the test.
- In a rolled-back transaction with roles `anon` and `authenticated` holding ALL grants, the migration's revoke block leaves them no table or EXECUTE privilege, and a non-owner role with SELECT sees 0 of 13 agents rows under RLS.
- `pnpm verify:fast` passes.

## Known gaps
- `submitted` is never set: verification is synchronous inside `submitCapture`.
- A `verified` task whose transfer failed for an already onboarded worker is retried only on the next `worker.onboarded` event. A dispute between settle and transfer cannot stop that transfer.
- Concurrent `workerConnectUrl` calls for one worker rely on the Stripe adapter's per-worker idempotency key (`eyes-worker-account-<worker_id>`, PR #5) so no orphan account is created.
- InsForge admin-role EXECUTE grants and RLS bypass for the SECURITY INVOKER functions need the G1 live smoke.
- `eyes_nearby_workers` scans all available workers (no geo index); fine for a demo pool. `owner_email` from signup is not stored (no column).
