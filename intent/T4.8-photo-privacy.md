## Why
Every capture is uploaded before vision judges it, so a photo rejected for `prominent_faces` kept a permanent public URL in the InsForge `photos` bucket, and the agent got that URL from `await_answer` and `get_task` (issue #27). SPEC §12 promises no identifiable people; this is the one photo we know shows a face.
## What
- `Storage.deletePhoto({ key })` added to the provider contract (ADR-014); `fakeStorage` drops the key from its map, `createInsforgeStorage` calls the SDK's `bucket.remove(key)` and throws its error.
- `submitCapture` keeps the upload key, wraps the `Vision` provider it hands to `verifySubmission` to record `prominent_faces`, and when it is true deletes the object and stores `photo_url = null` on the submission. A delete failure is logged as `photo delete for task <id> failed` and the submission continues with `photo_url = null`.
## Decisions & alternatives rejected
- Delete after reject over judge before upload: the latter needs `VisionJudgeInput` to carry bytes, a new image source in `createClaudeVision` and a `packages/verify` change, and the photo would still be uploaded after approval (ADR-014).
- Read the verdict through a wrapped `Vision` rather than adding `prominent_faces` to `VerificationResult` (second contract change, another builder's package) or parsing `vision_reason` text.
- Never store the URL rather than store-then-null: one write, and the agent-facing paths (`answerOf`, email reply, dashboard feed) all read `submissions.photo_url`, so null there covers them all.
- The engine diff stays in the upload/verify/`eyes_submit` block of `submitCapture`; the payout code that PR #45 edits is untouched.
## Assumptions
- InsForge delete is `DELETE {INSFORGE_BASE_URL}/api/storage/buckets/photos/objects/{encodeURIComponent(key)}` with `Authorization: Bearer <INSFORGE_API_KEY>`, response `{ "message": "Object deleted successfully" }`. Source: installed `@insforge/sdk@1.5.2` `StorageBucket.remove` (`dist/index.mjs`, `dist/client-*.d.ts`) and https://docs.insforge.dev/sdks/rest/storage.md "Delete Object". The SDK retries DELETE on 5xx and network errors and returns 4xx as `{ error }`, which we throw. The admin key may delete in a public bucket because it already uploads there.
- `submissions.photo_url` is nullable (`001_init.sql`) and `eyes_submit` takes a nullable `p_photo_url` (`002_engine.sql`); no migration.
## Verification
- `packages/engine/src/engine.int.test.ts` (real Postgres, fake providers): (1) a capture whose verdict has `prominent_faces` goes to `needs_review`, vision saw the uploaded URL, no object for the task is left in `fakeStorage`, and `await_answer` and `get_task` return `photo_url: null`; (2) captures without faces, approved and sent to review for not answering, keep the object and return its URL; (3) `deletePhoto` rejecting still returns `needs_review`, logs exactly `photo delete for task <id> failed`, and `get_task` returns `photo_url: null`. The shared `verifySubmission` stub now calls `vision.judge` like the real one; with the default verdict it returns the same `PASS` as before.

## Known gaps
- The face photo is public for the seconds between upload and the verdict; judging bytes before upload would close that (ADR-014).
- A failed delete leaves the object in the bucket under its unreturned random key; there is no retry or sweep.
- If the judge times out in `verifySubmission`, the late verdict is ignored and the photo is kept for manual review.
- Not live-verified against the InsForge project.
