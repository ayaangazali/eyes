## Why
An agent that has never heard of Eyes must get from "here is a URL" to a verified answer using only public docs: sign up, hand the top-up link to its human, connect MCP, then quote, ask and loop on await. These are the files apps/mcp serves at `/llms.txt`, `/llms-full.txt`, `/openapi.json` and `/.well-known/agent-card.json`, plus a CLI so the same capabilities work from a shell (§9) without ever escrowing twice on a retry (ADR-010: money and idempotency are blocking).

## What
- `docs/public/llms.txt` (hand-written, 91 lines, llmstxt.org shape): scope, pricing, escrow and refunds, the 4-step quickstart with `claude mcp add` and a `.mcp.json` snippet, every status including `needs_review`, errors with `fix`, the MCP "Input validation error" exception, safe key reuse, and the CLI (`eyes` means `node cli/src/main.ts`; `--no-wait` then `status`/`await` for agents with tool-call timeouts).
- `docs/public/agents.md` and `docs/public/robots.txt` (allow all, Claude-User and ChatGPT-User named).
- `cli/src/docs.ts` generates `openapi.json` (OpenAPI 3.1, every `HTTP_ROUTES` entry except health, webhooks, browser redirects and `/w/*`; schemas via `z.toJSONSchema`; bearer scheme; `Error` with `error`, `message`, `fix`), `llms-full.txt` (llms.txt plus signup, per-tool route, summary, example, JSON Schemas and the `ERRORS` catalog) and `.well-known/agent-card.json`. `pnpm --filter @eyes/cli gen:docs` writes them.
- `cli/src/main.ts`: `eyes signup|ask|await|quote|status|cancel|dispute|balance|policy`, `--json` (one JSON object per line), `-h/--help`, config at `~/.config/eyes/config.json` (0600) with `EYES_API_URL`/`EYES_API_KEY` overriding it, arguments checked against the zod contracts before any request (numbers must be plain decimals).
- `ask` idempotency (round 5): `--idempotency-key` wins and touches no file. Otherwise each ask has its own file `~/.config/eyes/pending-asks/<sha256 of api_url, api_key and the schema-normalized ask parameters>.json` (0600, dir 0700) holding `{idempotency_key, task_id}`. It is created with flag `wx` before the POST: the winner of a same-instant race writes a random key, every loser reads the winner's file (retrying briefly while it is still empty) and reuses that key. After the POST the file gets the task_id. A later identical `ask` reuses the key unless `GET /v1/tasks/<task_id>` shows a settled status (expired, refunded, disputed, verified, paid, needs_review); only then is the file rewritten with a successor key derived from the settled task_id (`sha256("eyes-next-ask:" + task_id)`) and `task_id: null`. A failed status lookup keeps the key. The wait loop never touches the file (round 6). Rewrites go to a temp file in the same directory (0600) and are renamed into place, so a crash leaves the old or the new content, never an empty file. Before each rewrite the file is read again, and the write happens only if it still holds the idempotency_key this process read (T4.7, #42); if the chain moved on, the settled-check path starts over from the current file and the post-POST write is skipped. There is no shared file and no read-modify-write of another ask's state. If the file cannot be created, nothing is sent and the fix says to pass `--idempotency-key`. If it is empty after the 1 s retry (only a crash inside the `wx` create, before any key is printed, leaves that), the fix says nothing was sent and to delete the file and re-run. Any other unreadable content keeps the fix that says to pass the last key printed on stderr for this ask. The key is printed to stderr before the POST.
- Wait loop (`ask` and `await <task_id> [--timeout <seconds per poll>]`): retries in place on `rate_limited`, network errors and any HTTP >= 500 (HTML gateway pages included), backoff 1, 2, 4 .. 30 s, reset by a successful poll; gives up after 10 minutes of consecutive failures ("the server is temporarily failing" for 5xx). Errors leaving the loop carry `task_id` and the key; Ctrl-C prints `resume with: eyes await <task_id>` (exit 130); permanent errors (task_not_found, unauthorized, invalid_input) get no resume line. The final status is printed once.

## Decisions & alternatives rejected
- Agent card follows A2A 1.0 (orchestrator ruling): no top-level `url`; `/mcp` and `/` live in `supportedInterfaces` with custom binding URIs. `/w/*` worker routes are left out of openapi.json.
- The owner console routes (`owner_console`, `owner_policy`) are excluded from the agent docs by design (ADR-011: the agent never sees the owner link). The generated error catalog still lists `owner_link_invalid`, like the worker-only `offer_invalid`, because it lists every `ERRORS` code and holds no link.
- One file per ask, created with `wx` (human decision A, round 5), replaces round 4's shared `pending-asks.json`, whose read-then-write let two concurrent different asks erase each other's entry.
- A settled ask's file is rewritten with a successor key derived from the settled task_id instead of being deleted (deviation from the round-5 instruction "delete the file when the task is final", raised in the reply). An unconditional delete races with the `wx` create: a slow deleter can remove the fresh file of a re-run that already sent its key, and the next re-run then creates a random key and a second task. Because every process that sees the same settled task derives the same successor key, concurrent re-runs agree without any compare-and-swap. A late writer can at worst set the file back to an older key, whose task the server returns again; it can never mint a new key for an open task.
- The wait loop no longer rewrites the file on a final status (round 6, verifier major). That rewrite was unconditional and ran up to minutes after the file had moved on, so it could erase a newer ask's task_id and make the next identical ask replay a settled task. The status lookup in the next `ask` derives the same successor key, so the rewrite added nothing.
- Resume text uses `eyes` literally (human ruling, round 4); llms.txt and `--help` say `eyes` means `node cli/src/main.ts`.
- CLI-only error codes `network_error`, `unexpected_response`, `config_error` and `interrupted` let `--json` callers tell a transport failure from a server answer. Retry notices go to stderr.
- The docs freshness test compares parsed JSON for the JSON files and exact text for llms-full.txt; Biome owns JSON formatting. Tool summaries live once in `TOOL_DOCS`.

## Assumptions
- REST semantics from apps/mcp (`server.ts`): JSON bodies, `task_id` in the path, `/await` body `{timeout_seconds?}`, error bodies from `EyesError.toBody()`, docs read from `docs/public/<path>`.
- The engine makes `ask` idempotent per `(agent_id, idempotency_key)` and returns the existing task for a repeated key (verified live in `ask.int.test.ts`). A small file written in one `writeFile` is read either empty or complete on local filesystems; empty or unparsable reads are retried for up to 1 s. Answered = verified, paid, needs_review; final = expired, refunded, disputed.
- ADR-007 (`email_address`, `LocationInput` text) and ADR-008 (`timeout_seconds` text) are in the generated docs. The engine always fills `top_up_url`.

## Known gaps
- A crash between writing the temp file and the rename leaves an orphan `<file>.<uuid>.tmp` (under 100 bytes) in `pending-asks/`.
- Serving `/robots.txt` and `/agents.md`, and absolute URLs in the agent card, are apps/mcp work (T2.4). Docs stay relative until then.
- No license file: humans decide.
- The CLI is not published to npm; agents run it from the repo.
- Files for asks that are never re-run or awaited to a final status stay in `pending-asks/` (about 100 bytes each). They hold no secret beyond an idempotency key.
- The `/mcp` request body in openapi.json is optional because its schema has no required fields.
- Fixed in T4.7 ([#42](https://github.com/ayaangazali/eyes/issues/42)): the stale write-back and the empty pending file. The re-read and the rename are still two steps, so a write can land over a change made in the microseconds between them (was one HTTP round trip).
