# ADR-022: Worker texts and pages say when payouts are simulated

Status: proposed (2026-10-17, T4.24 builder; the `AppConfig` flag was requested by the orchestrator). Adds to the frozen contract: `live_payouts: z.boolean().default(false)` on `AppConfig`, and a required `live_payouts: boolean` on `OfferMessage` and on the `Messaging.sendPaid` message.

## Context
The deployed server runs `EYES_PROVIDERS=live` with real Inkbox texting and real Claude vision but no `STRIPE_SECRET_KEY`, so `liveProviders(env).payments` is false and the fake `Payments` provider is wired. Real people now get texts, and on that configuration several of them were false:
- START answered "Set up payouts here: <link>", and `/w/connect/<token>` redirected to the fake provider's `https://connect.fake.test/onboard/...`, a host that does not resolve.
- A worker who had opened that link got a fake transfer after a verified answer and the text "you've been paid $3". A worker who had not got "Your $3.00 for this task is waiting. Set up payouts here: <link>".
- Offers said "Eyes: $3 to check ...", the capture page said "$3.00 for this task" and "Verified, payout pending", and the JOIN page said checks pay $3 through Stripe and that START brings a payout setup link.

The engine, comms and the route layer could not tell a simulated payout from a real one: `Providers.payments` is the same interface either way. `/status` and HOME already say "Payments are simulated: no real money moves." The same class of problem for owner email was fixed by ADR-018.

## Decision
- `AppConfig.live_payouts` (default `false`) says whether payouts move real money. `apps/mcp/src/main.ts` sets it from `liveProviders(env).payments`, the same decision that picks `createStripePayments` over the fake, so the flag and the wired provider cannot disagree on a deployed server. `scripts/resolve-task.ts`, which builds its own config and can release a payout, sets it the same way.
- The engine words its own texts from the flag. When it is false: START keeps "You are in. Eyes will text you paid tasks nearby." and replaces the payout link with "This is a test server and payouts are simulated, so no real money is paid."; HELP, the not-signed-up reply and `opt_in_instructions` add that sentence (and `opt_in_instructions` drops "we reply with your payout setup link"); the capture result says "Verified." or the manual-check text followed by that sentence; and a verified answer from a worker with no payout account gets the same notice as a paid one (below) instead of the payout-link text. No connect link is sent anywhere.
- Offers and the paid notice are worded in `packages/comms`, so the engine passes the flag on those messages as `live_payouts`. When it is false the offer starts "Eyes test ($0):" and names no amount, and the paid notice says "your answer for the task at <place> was accepted. No money was sent because payouts are simulated on this test server." Both still go through `placeText`, so no raw `place_label` reaches a text.
- `/w/connect/<token>` with simulated payouts answers a short "Payouts are simulated" page and does not call `workerConnectUrl`, so it mints no onboarding link and creates no fake account. The earnings page shows "the amounts on this page are not real money and nothing is sent to you" in place of the payout-setup note, and each task's payout column reads "Simulated, nothing sent".
- The worker web is a static build, so it gets a build-time `VITE_LIVE_PAYOUTS`, like `VITE_INKBOX_CONNECT`. Unless it is `"true"`, the JOIN page shows "This is a test server. Payouts are simulated, so tasks pay no real money." and hides the "$3 through Stripe" sentence and the payout-link step, and the capture page shows "Test task, no real pay" and a plain "Verified" heading. The HTML defaults are the simulated state.
- The money flow does not change. A worker who already has a fake account still gets the fake transfer, and the task still reaches `paid`; only the words change.
- Default `false`: a config or build without the setting never promises real money. Harnesses that run the payout flow with the fake provider standing in for Stripe (engine and payments integration tests, golden path, demo rehearsal, `scripts/swarm.ts`) set `live_payouts: true`, and the golden web build sets `VITE_LIVE_PAYOUTS=true`.

## Alternatives rejected
- A `simulated` flag on the `Payments` provider or a `createInkboxMessaging(env, livePayouts)` option: a second copy of a fact the entry point already decides, which the fake messaging outbox could not show to the integration tests. Carrying it on the two messages keeps one source (the config) and lets tests read it from the payload.
- Sending the simulated paid notice with `sendText`: it would need the place sanitizer outside comms, or drop the place, and it loses the `paid:<task>:<phone>` idempotency key that keeps a retried send from texting twice.
- Skipping the fake payout when payouts are simulated: it changes task status and the ledger, which the agent-facing tools and the ops feed read, for a change that is only about what workers are told.
- Wording the JOIN page so it is true in both modes: "get paid" is the pitch of the live product, and only a notice that appears on a simulated build makes the page true without weakening the live one. The cost is one more build variable to keep in step with the server's Stripe key; the safe default (simulated) means forgetting it under-promises.
- Fetching the payout mode from the API at page load: a new request and a runtime dependency for a value that only changes when the deploy changes.

## Consequences
Every `AppConfig.parse` caller gets `live_payouts: false` without edits, so a harness that wires real Stripe and builds `AppConfig` itself must set `live_payouts: true`, or its workers are told no money was sent when it was. Every caller of `sendOffer` and `sendPaid` must pass `live_payouts`; TypeScript enforces it. When Stripe goes live, the worker web must be rebuilt with `VITE_LIVE_PAYOUTS=true` (docs/DEPLOY.md section 3). Link-preview meta tags (`og:title`, `og:description`) on the JOIN and capture pages still say "get paid": crawlers read the static HTML without running scripts, so they cannot follow the build flag without HTML templating.
