# ADR-023: A separate keyless sandbox server with a simulated worker

Status: proposed (2026-10-17, T4.29 builder). No change to the frozen contract (`packages/core`, migrations).

## Context
Every Eyes tool needs `Authorization: Bearer <api_key>`. Manufact Cloud's eval suites, Public Chat and Inspector can only authenticate to a server through OAuth (`/api/v1/servers/{id}/credentials/connect` is OAuth-only), so today they cannot call a single Eyes tool, and neither can a judge who has not signed up. Making the live server keyless is not safe: `ask_eyes` offers tasks to real opted-in workers from the shared `workers` table, and a real person's YES could claim a task nobody paid for.

The task plan asked for one ephemeral agent per MCP session. mcp-use 2.10 is stateless: it builds a fresh SDK server for every HTTP request, issues no `mcp-session-id` (checked with a probe on 2026-10-17: the initialize response has no such header and every later request arrives without one) and answers GET and DELETE on `/mcp` with 204 or 405 (`docs/vendor/mcp-use-manufact.md`). There is no session to key an agent on.

## Decision
- A second server with its own InsForge project runs the same image with `EYES_SANDBOX=1`. `apps/mcp/src/main.ts` refuses to start with it when `EYES_PROVIDERS=live` (any provider could be real), `EYES_FAKE_WEBHOOKS` is set (anyone could credit balances) or `ANTHROPIC_API_KEY` is set (keyless callers would spend billed classifier calls), and says why. The sandbox runs the safety rules only.
- Keyless access (`apps/mcp/src/sandbox.ts` `keylessAgents`, wired into the existing bearer middleware in `server.ts`): only when `EYES_SANDBOX=1` and the request has no `Authorization` header at all, `/mcp` and `/v1/*` get a sandbox agent. A request with any `Authorization` header goes through `service.authenticate` exactly as before, so a bad key is still 401. The agent is keyed on the caller's address, the same right-most `X-Forwarded-For` key (IPv6 by /64) the signup throttle uses, and kept in memory as address -> api key for an hour after its last request, at most 10,000 addresses, oldest dropped first. Concurrent first requests from one address share one creation. If the held key stops authenticating (for example after an owner-link key rotation), that request is 401 and the address is forgotten, so its next request gets a new agent.
- A new keyless agent is made with the existing service calls: `signupAgent`, then `updateSpendPolicy` with an owner token signed by the server (daily cap 1,000 USD, the most `OwnerPolicyInput` allows; max bounty 10 USD; every task type). Whenever a keyless agent's balance is under 100 USD, `creditTopup` adds 1,000 USD of play money under a `sandbox:<uuid>` ref. At most 30 keyless agents are created a minute across all callers; past that the call gets `rate_limited` with `retry_after_s`. The daily cap stays on and is the per-address limit: about 285 tasks per UTC day.
- The simulated worker (`createSandboxService`) wraps the fake messaging provider the engine is built with, so it reacts to the texts the engine sends, through the existing service methods. It acts only for sandbox numbers (`+1`, an area code, then `55501` and two digits, the fictional 555-01XX range): any other worker is never answered for, so a sandbox pointed at a database with real workers would not claim or capture in their name. An offer to a sandbox number is answered YES at once (`handleWorkerReply`), and the capture link that YES gets back is used 5 seconds later: `getOffer` for the task's coordinates and type, then `submitCapture` at those coordinates with a fresh `captured_at`, an answer text that starts "Simulated sandbox answer, nobody went:", and a 12-byte JPEG header. The fake vision provider passes it, so the task reaches `verified`.
- `ask_eyes` makes sure a worker is free nearby: when its quote is allowed and shows `workers_nearby` 0, a worker with a random number in that range is joined at the resolved location and texts START (up to three tries, in case a random number is already taken elsewhere). Workers are reused after they answer, so the pool grows only with concurrency and with new areas. `quote_task` writes nothing: when it is allowed and sees no free worker it reports `workers_nearby` 1 and `est_minutes_to_answer` 1, because the ask will add one, and the sandbox note says so.
- `ask_eyes` runs one at a time per process. Its quote, its dispatch and the immediate YES finish before the next ask is posted, so a worker's YES always claims the task it was just offered (`eyes_claim` takes the worker's newest dispatched offer) and a free worker seen by one quote is not taken by a parallel ask. Without this, three parallel asks at one place failed every time in the integration test with `no_workers_nearby`. Each ask gets 15 seconds once its turn comes and at most 10 wait; past either, the call gets `rate_limited` (`retry_after_s` 15, retry with the same `idempotency_key`), so one stalled database call holds the others for at most 15 seconds.
- Honest surfaces: HOME and `/status` show "Sandbox: keyless, simulated worker, no real people or money." with how to call it, and drop the "no task gets answered" texting line, which the simulated worker makes false. The same notice also says that `quote_task` counts the worker an ask adds and that place names resolve only for the three demo places, so any other place needs `{lat, lng}`; it opens the MCP instructions and the `quote_task` and `ask_eyes` descriptions (that geocoding sentence replaces the separate place-lookup line on HOME and `/status`). The server description starts with the sandbox sentence, and every `ask_eyes` and `await_answer` `next_step` starts with it plus "A simulated worker answers each task in about 5 seconds."

## Alternatives rejected
- Keyless on the live server, or a sandbox flag per agent there: dispatch reads the shared `workers` table, so a real worker could claim a sandbox task, and a bug in the flag would hand out real tasks for free.
- One agent per MCP session: there are no sessions (above).
- One fresh agent per request: `await_answer` checks that the task belongs to the caller, so the answer would be `task_not_found`.
- One shared agent for every keyless caller: judges, Manufact and anyone else would share one task list and one set of idempotency keys.
- Keeping the default 20 USD balance and daily cap: Manufact's evals, Inspector and Public Chat reach us from Manufact's addresses, so they share one agent, and five tasks a day would stop the evals the sandbox exists for.
- Claiming after a delay: with workers shared between tasks, a late YES claims the worker's newest offer, which can be another task, and the first task is never claimed.
- A new worker per task, opted out after its answer: more joins and texts per task for no gain, since a free worker nearby answers just as well.
- Bypassing the engine (writing tasks or submissions directly): it would skip the rules layer, escrow, verification and settlement that the sandbox is meant to exercise, and needs new RPCs.

## Consequences
- Callers behind one address share an agent: Manufact's evals, Inspector and Public Chat see each other's tasks in `list_tasks`, and one idempotency key reused with different parameters gets `idempotency_conflict`.
- At most 30 keyless agents a minute across all callers is a shared budget: one caller with many addresses (an IPv6 /48 holds 65,536 /64 keys) can use it up and make new keyless callers wait up to a minute for their first request. Addresses that already hold an agent keep working. Accepted for a sandbox with play money; counting per /48 would add a second key scheme for this one limit.
- An ask that times out may still finish in the background and post its task; the retry with the same `idempotency_key` then returns that task instead of charging again. After a timeout the next ask can run while the late one finishes, so the one-at-a-time guarantee holds only within the 15 seconds.
- `cancel_task` on a sandbox task always answers `task_not_cancellable`, because the simulated worker claims at dispatch.
- The keyless map, the ask queue and pending captures live in memory. A restart gives every address a new agent (earlier task ids then answer `task_not_found`), and a task claimed but not yet captured stays `claimed` until its deadline, then expires and is refunded. The serial queue assumes one server instance.
- `photo_url` points at the fake storage host `storage.fake.test`, which does not resolve. The fake messaging outbox and fake photo store grow by a few hundred bytes per task until restart.
- `/llms.txt`, `/openapi.json` and the agent card still describe bearer keys and real workers; HOME's join button still leads to the live worker site. The sandbox notice and the tool texts above are what tell a caller it is a sandbox.
- `est_minutes_to_answer` still assumes walking time (3 minutes at distance 0) when a worker is already free, while the simulated answer comes in about 5 seconds.
- The sandbox number check keeps the simulator from acting for real workers, but it cannot stop `ask_eyes` from joining fictional workers into whatever database it is given. Keeping the sandbox on its own InsForge project is a deploy rule (`docs/DEPLOY.md`), not something the code can check.
