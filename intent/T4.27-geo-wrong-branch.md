## Why
Issue #78: live on 2026-10-17, `POST /v1/quote` with `"location": "Philz Coffee, 3101 24th St, San Francisco"` resolved to "Philz Coffee, 4298, 24th Street, Noe Valley, ...", a different branch 2.08 km from 3101 24th St. `createNominatimGeo` took Nominatim's first hit (`limit=1`) without checking it, so a chain name plus a street can land on the wrong store. Workers near the wrong store get the offer and the GPS check passes there, so the agent pays for an answer about a place it did not ask about.

## What
`apps/mcp/src/geo.ts`: the house number is the number that starts a comma-separated part of the query and is followed by a word ("3101 24th St", "548 Market St"). A number inside a part ("Suite 200", "CA 94105", "Super 8", "Pier 39") or glued to other text ("24th", "7-Eleven") is not one. With no house number the lookup behaves exactly as on main. With one, a hit is trusted only if that number is one of the tokens of its `display_name` split on spaces, commas, semicolons and hyphens, so OSM's multi-number buildings ("135;141;149, Powell Street") match. If the first hit is not trusted and the house number is in a middle part (business name before it, city after it), it waits 1.1 s and searches once more from the house-number part onward, "3101 24th St, San Francisco", trusting that hit only if it has the number. Otherwise it returns null, which the engine turns into `location_not_found`. The Nominatim request moved into a `search` helper so both calls share the URL, user agent, 5 s timeout and HTTP error. Pinned places, `lat,lng` strings and the cache are unchanged; the cache key is still the original query and holds the final result.

## Decisions & alternatives rejected
- Number check on the hit, not structured search (`street=`, `city=`, issue option 3): parsing free text into street and city is a parser to maintain, and the free-form address search already lands on the right building (Verification).
- Retry also when the first search has no hit but the query has a house number in a middle part: the same business-name-blocks-the-address case, and it keeps the code to one check.
- 1.1 s wait before the retry (round 1 verifier): Nominatim allows at most 1 request per second, and two requests back to back from the live server's IP risk a 429 (which surfaces as `internal_error`) or a block. The wait only happens on the mismatch path, which is rare, and the cache means it happens once per query.
- No retry when the house number is in the first part ("548 Market St, Suite 200, San Francisco"): dropping parts before it would drop nothing, and dropping the address itself (round 1 did) searches for "Suite 200, San Francisco". No retry when it is in the last part: the retry would lose the city and could land on the same address in another city.
- Number matched as a whole token on both sides, not a substring, so "31" does not match "3101" and a postcode does not match a house number inside it.

## Assumptions
- Nominatim `display_name` lists the house number as its own part ("4298, 24th Street") or as a `;`-separated list ("135;141;149, Powell Street"), as in the live hits below.
- An address part starts with its house number, US style. A business name that starts with a number ("24 Hour Fitness, 1200 Van Ness Ave") is read as house number 24; its own label has "24", so that query behaves as on main.

## Known gaps
- The `location_not_found` fix lives in `packages/core/src/errors.ts` (contract, ADR-017). It leads with "Pass the coordinates as numbers ... coordinates always resolve", which is the reliable way out for a chain store, but it does not suggest a full street address, and its "place name, city" option for a chain without a number still takes the first hit as before. Left unchanged here; `quote_task` already says to retry with `{lat, lng}` when `resolved_location` is not the place meant.
- After a retry the label names whatever OSM has at that address ("La Rancho Market, 3101, 24th Street"), not the business the agent typed. The coordinates are right.
