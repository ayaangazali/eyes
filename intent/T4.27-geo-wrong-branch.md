## Why
Issue #78: live on 2026-10-17, `POST /v1/quote` with `"location": "Philz Coffee, 3101 24th St, San Francisco"` resolved to "Philz Coffee, 4298, 24th Street, Noe Valley, ...", a different branch 2.08 km from 3101 24th St. `createNominatimGeo` took Nominatim's first hit (`limit=1`) without checking it, so a chain name plus a street can land on the wrong store. Workers near the wrong store get the offer and the GPS check passes there, so the agent pays for an answer about a place it did not ask about.

## What
`apps/mcp/src/geo.ts`: when the query has a standalone house number (a digit group bounded by start, space or comma, so "3101" counts and "24th" or "7-Eleven" do not), a hit is trusted only if its `display_name` has that same standalone number. If the first hit is not trusted and the query has 3 or more comma-separated parts, it searches once more without the first part (the business name), "3101 24th St, San Francisco", and trusts that hit only if it has the number. Otherwise it returns null, which the engine already turns into `location_not_found`. The Nominatim request moved into a `search` helper so both calls share the URL, user agent, 5 s timeout and HTTP error. Pinned places, `lat,lng` strings and the cache are unchanged; the cache key is still the original query and holds the final result.

## Decisions & alternatives rejected
- Number check on the hit, not structured search (`street=`, `city=`, issue option 3): parsing free text into street and city is a parser to maintain, and the free-form address search already lands on the right building (Verification).
- Retry also when the first search has no hit but the query has a house number: the same business-name-blocks-the-address case, and it keeps the code to one check. Queries without a house number behave exactly as before.
- Not changing the `location_not_found` fix: it lives in `packages/core/src/errors.ts` (contract, ADR-017) and already leads with "Pass the coordinates as numbers ... coordinates always resolve", which is the reliable way out for a chain store. `quote_task` text already says to retry with `{lat, lng}` when `resolved_location` is not the place meant.
- No 1 s sleep before the retry: the server has no global Nominatim throttle today, the retry happens at most once per uncached query, and a sleep would add a second to every mismatched quote. Same user agent and timeout as the first request.
- Number matched as a standalone token, not a substring, so "31" does not match "3101" and a postcode does not match a house number inside it.

## Assumptions
- Nominatim `display_name` lists the house number as its own comma-separated part ("4298, 24th Street"), as in both live hits.
- The house number is the first standalone digit group in the query. A query with a standalone number that is not a house number (a postcode, "Pier 39") still works when Nominatim's label contains it, and returns `location_not_found` otherwise.

## Verification
- Live Nominatim, one request with the server's user agent, `q=3101 24th St, San Francisco`: `"lat":"37.7523636","lon":"-122.4142890"`, `"display_name":"La Rancho Market, 3101, 24th Street, Mission, San Francisco, California, 94110, United States"`. That is 58 m from 37.7527,-122.4148 and has "3101", so the retry lands on the right building. The label names the shop OSM has at that address, not Philz.
- `pnpm exec vitest run apps/mcp/src/geo.test.ts`: 3 passed. New case: Philz 3101 retries with the address and returns the 3101 hit; Philz 4298 keeps the first hit with one request; 9999 retries and returns null; exactly 5 requests in that order. The existing cases still cover pinned places and `lat,lng` (no fetch) and a query without a house number (first hit kept, cached).
- Fail on old: with origin/main `geo.ts` the new test fails at the 3101 assertion (got the Noe Valley hit), and with that assertion removed it fails at the 9999 assertion ("expected { lat: 37.75, ... } to be null").
