## Why
The SPEC coverage ledger and the UX audit found that a worker who texts STOP gets no reply, so they cannot tell it worked, and that HELP did not say where to read more. docs/DEPLOY.md also mentions an Inkbox cap of 40 new recipients per 24 h that nothing counts. This task closes the two reply gaps and checks whether the cap applies to us.
## What
- STOP from an opted-in worker: the opt-out commits first, then one text: `Eyes: you're opted out and won't get task texts. Text START to rejoin.` (70 chars). A repeat STOP, or any other reply before START, gets nothing (the existing `!worker.opted_in` guard).
- START from an opted-out worker already got `You are in. Eyes will text you paid tasks nearby. Set up payouts here: <link>`. That is unchanged and now tested after a STOP.
- HELP: `Eyes texts you paid tasks to check public places nearby. Reply YES to claim a task, STOP to opt out. More: <EYES_WORKER_WEB_URL>`. It is 106 chars plus the URL, so 137 chars with the deployed `https://7t6779x4.insforge.site`. A URL of up to 53 chars stays within 159.
- No new-recipient counter. See the next section.
## Decisions & alternatives rejected
- New-recipient budget, decided from the vendor docs: no counter. docs/vendor/inkbox.md says a dedicated line can initiate with "40 new recipients/24 h". The page it cites (https://inkbox.ai/docs/capabilities/imessage.md, re-read 2026-10-17) says: "Dedicated lines also limit agent-initiated conversations to 10 new recipients per rolling hour and 40 per rolling 24 hours. Existing recipients and recipients who message the line first do not consume these first-contact slots." Eyes never texts anyone first. `workers.opted_in` defaults to false (001_init.sql). Only `eyes_set_worker_opt_in` sets it, and it is called with `true` only from `handleWorkerReply` on START, which runs only for a signed inbound message from that phone. `eyes_nearby_workers` returns only `opted_in` workers (006). Every other send replies to an inbound message: claim replies, HELP/NO/unknown, and the "not signed up" reply. So no send uses a first-contact slot.
- The texts stay in the engine, not in packages/comms as the task card said. The engine already writes every free-text reply (START, NO, HELP, unknown, no open task) and sends it through `Messaging.sendText(to, body)`. The frozen `Messaging` interface (packages/core) has no STOP or HELP method. Importing templates from `@eyes/comms` would make the engine depend on a vendor package (`@inkbox/sdk`, `@primitivedotdev/sdk`, `hono`) and cross the ADR-003 seam. So packages/comms is unchanged; its parser already maps STOP, START, HELP, INFO and a lone `?`.
- Opt-out commits before the confirmation is sent. If the send fails, the worker is still opted out and the webhook route logs the failure. Sending first was rejected: a failed write would leave a worker who was told "you're opted out" still getting offers.
- No confirmation for a worker who never sent START and texts STOP. The schema cannot tell "never started" from "stopped" without a new column, and the existing adversarial test "a worker who never sent START gets no text for anything but START" pins that silence.
- HELP from an opted-out worker stays silent. The task card says to send nothing after the STOP confirmation until START. Answering HELP for opted-out numbers (common carrier practice) was rejected for that reason.
- HELP dropped "START to resume". Only opted-in workers get HELP, and the space goes to the URL. The old text plus the deployed URL was 157 chars, which left 2 chars of headroom.
## Assumptions
- Links are allowed in the HELP reply. imessage.md limits links, phone numbers and 159+ chars only "before the first reply", and a HELP sender has already texted START and now HELP. The capture link after YES and the payout link after START already rely on this.
- On an SMS line Inkbox blocks every send after STOP (`403 recipient_opted_out`, https://inkbox.ai/docs/api/phone/texts.md), so the confirmation would fail and be logged while the opt-out stands. The deployed line is iMessage, and the docs do not say whether Inkbox acts on STOP there (open question in docs/vendor/inkbox.md).

## Known gaps
- The payout paths (`payOut` -> `sendPaid`, and the "your $X is waiting" text in `submitCapture`) can still text a worker who sent STOP while holding a claimed task. PR #45 (T4.2) owns those paths. Fix after it merges: skip those texts when `!worker.opted_in`.
- docs/vendor/inkbox.md and docs/DEPLOY.md say "40 new recipients per 24 h" without "agent-initiated only". They also leave out the 10-per-hour window. A docs follow-up should add that workers who text START first do not count.
- The plan-level rolling 24 h outbound cap ("varies by plan", `429` with `Retry-After`) is not counted. An offer rejected with 429 is dropped by `Promise.allSettled` and not counted in `workers_notified`.
