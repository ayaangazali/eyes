## Why
Chat apps that render MCP Apps (ChatGPT, Claude) can show a tool result as a card instead of raw JSON. Eyes' answer is visual (a place, a verified answer, a live photo, three checks, a cost), and today a user only sees it if their agent copies fields into prose. Manufact's mcp-use ships views for exactly this, but Eyes runs its own HTTP server (`node apps/mcp/src/main.ts` behind a byte-safe Node adapter) instead of `mcp-use start`, so nothing in the repo showed whether views work in our server at all. There was also no documented way to reach a local server from a hosted client or the Inspector.

## What
- `apps/mcp/views/task-card/view.tsx`: a React view started from the `create-mcp-use-app --template mcp-apps` starter, cut down to one component. It reads the tool result with `useToolContext()` and shows the status, place, question, the answer (yes/no prefix when `answer_bool` is set), the photo, when and how far from the place it was captured, the three checks with the vision reason, and the bounty plus fee as held, cost or refunded. A missing photo or one that fails to load shows "No photo to show".
- `apps/mcp/src/server.ts`: a tenth tool, `show_task`, with `get_task`'s input and output schemas, behavior hints (read-only, not destructive, closed world, as T4.31 set them) and handler (`service.getTask`), so its JSON result is identical. At startup `createServer` reads the mcp-use build manifest (`apps/mcp/.mcp-use/build/manifest.json`, or `EYES_VIEWS_MANIFEST` in tests); when it holds the `task-card` view, the server primes it with `server[registerViews]` (the same call the wrapper generated by `mcp-use build` makes) and binds it to `show_task`, with the InsForge origin in the view's CSP `resourceDomains` so live photos load. Without the manifest, `show_task` is a plain read-only tool.
- `apps/mcp/views/entry.ts` and the `build` script in `apps/mcp/package.json`: `mcp-use build --inline --entry views/entry.ts` compiles the view and embeds its JS and CSS in the manifest. `react` and `react-dom` 19.3.0 are devDependencies of `@eyes/mcp`.
- `Dockerfile`: `RUN pnpm --filter @eyes/mcp build` after install, so the deployed image serves the card. `.dockerignore` skips `**/.mcp-use` (a local build or a tunnel reservation never enters the image); `.gitignore` skips the generated `mcp-env.d.ts`.
- `scripts/smoke-live.ts`: the live tools/list check expects `show_task` too, so the post-deploy smoke does not fail on the new tool.
- `README.md`: the tools table and sponsor row say 10 tools; a "Task card, tunnel and Inspector" section under Develop locally gives the build, the fakes server, `npx -y @mcp-use/tunnel@0.2.2 3000`, a one-liner that prints a hosted or local Inspector link with the bearer header, and the `mcp-use screenshot` command.
- `docs/manufact/widget-task-card.png` (104 KB) and `docs/manufact/inspector-tools.png` (218 KB): the card rendered by `mcp-use screenshot`, and the hosted Inspector connected through the tunnel with the 10 tools listed and `show_task` rendered. Both from a task paid on fakes; neither shows a key.

## Decisions & alternatives rejected
- A new tool instead of a view on `get_task` or `await_answer`. mcp-use adds `_meta: { ui: { resourceUri } }` to every successful result of a view-bound tool (`wireResultMeta` in `mcp-use/dist/index-node.js`), so binding the card to an existing tool would change its JSON result for every non-UI client. `show_task` reuses `TOOLS.get_task`'s schemas, so `packages/core` and the nine existing tools' inputs, outputs, descriptions and results are untouched (the core contract snapshot passes unchanged) and no ADR is needed.
- Bind the view only when the build manifest exists. A view-bound tool on an unprimed server throws at mount ("bound to view ... but no views were primed"), which would take down every tool. Tests, CI and `node apps/mcp/src/main.ts` without a build all run without the manifest, so the binding follows the file.
- `--inline` instead of external assets. Inline puts the whole view in the `resources/read` HTML, so our server mounts no asset routes, our auth middleware and Node adapter see nothing new, and the CSP needs no asset origin. The cost is a 503 KB resource (React plus the mcp-use runtime), read once per host conversation.
- A two-line stub entry for `mcp-use build` instead of the real server. The build imports its entry, primes views on the default export and mounts it; `main.ts` listens and exits on missing env, and `createServer` needs a service. The stub makes the build print "View task-card is registered but no tool binds it", which is expected: the real binding happens in `createServer`.
- The standalone `@mcp-use/tunnel` (the client `mcp-use dev --tunnel` and `start --tunnel` use) instead of `mcp-use dev`/`start`: both import a default-exported server and call its `listen()`, which would bypass our Node adapter and `main.ts`'s provider wiring. No repo script either: two commands in two terminals.
- `react` and `react-dom` are the only new packages: `mcp-use build` bundles each view through its `bootstrapView` React runtime, and mcp-use lists both as peer dependencies it does not ship. They are devDependencies because only the build uses them.
- Main.ts and auth are untouched (a parallel task changes them).

## Round 1 changes
- An unreadable or foreign-shaped views manifest no longer stops the server: `taskCard` logs the error name and `show_task` is served as a plain tool, which is what the missing-manifest case already did. Test: a truncated manifest and `{}` both start, with no card.
- The card falls back to the raw status with neutral colours for a status it does not know, instead of throwing.
- Accepted cost: `show_task` repeats `get_task`'s schemas, about 4.6 KB more in tools/list (26,618 to 31,199 bytes), because putting the view on `get_task` would change its result for every non-UI agent.

## Assumptions
- InsForge public photo URLs live on the `INSFORGE_BASE_URL` origin (`https://<app>.<region>.insforge.app/api/storage/buckets/photos/objects/<key>`, docs/vendor/insforge.md). If a bucket redirects downloads to another host, hosts that enforce the CSP will block the photo and the card shows "No photo to show".
- The hosted Inspector moved: `inspector.mcp-use.com/inspect` now 301s to `inspector.manufact.com/inspect`, which 404s; the working path is `https://inspector.manufact.com/inspector?autoConnect=`. Its `autoConnect` accepts JSON with `customHeaders` (read from the `@mcp-use/inspector` 20.3.20 bundle, `parseAutoConnectParam`).

- Dev loop, run for real on fakes (`EYES_PROVIDERS=fake`, local Postgres, port 3430) with a task paid by a scratch script that follows `e2e/golden-path.spec.ts`: `npx -y @mcp-use/tunnel@0.2.2 3430` printed `Tunnel ready: https://extraordinary-lavender.tunnel.mcp-use.run`. ## Known gaps
- The view's CSP connect and resource domains come from the request origin; behind our Node adapter without `x-forwarded-host` that is `http://localhost`. The inline view loads nothing from our server, so only photos depend on the CSP, and those use the InsForge origin.
- Claude.ai and ChatGPT connectors expect OAuth or no auth, not a static bearer header, so the card shows there only once such a client can connect (the keyless sandbox task).
- Each `resources/read` of the card is about 500 KB.
