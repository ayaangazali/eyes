## Why
#62, the two findings deferred from the PR #61 verdict. When a worker replies NO after YES the task goes back to `dispatched`, but the other offered workers were told "already claimed" and nobody tells them it reopened, so the agent waits for a YES that never comes. And a NO that lands while the vision judge runs makes `eyes_submit` refuse the capture after the photo was uploaded, leaving a public photo that no submission row points to.

## What
- `013_reoffer.sql`: `eyes_reoffer(task, released_by, now)` sets `sent_at = now` on the task's existing offer rows for workers who are opted in, available and idle (the 006 rule: no `claimed` or `submitted` task), excluding the releaser, only while the task is `dispatched` and before its deadline. It returns those workers. EXECUTE revoked from PUBLIC, anon and authenticated, as in 010 and 011.
- `handleWorkerReply` NO: after the release text, calls `eyes_reoffer` and sends each returned worker the same offer through `Messaging.sendOffer` (distance from `distanceMeters`), with `Promise.allSettled` like `askEyes`. A NO with nothing to release is unchanged.
- `submitCapture`: when `eyes_submit` raises `task_already_claimed` or `offer_invalid` and a photo was uploaded (and not already deleted for faces), the stored photo is deleted. A failed delete logs `photo delete for task <id> failed` only. The original error is rethrown, so the worker sees exactly what they saw before.

## Decisions & alternatives rejected
- Migration 013 is needed for two reasons. Who was offered a task lives only in `offers`, and no RPC returns it (the engine reaches the database only through RPCs, InsForge in production). And `eyes_claim` claims the worker's newest `dispatched` offer by `sent_at`: without the bump, a worker holding a newer open offer would answer the re-sent text with YES and claim the other task. The test covers this case.
- No new offer rows: the existing rows are the original recipients, so the re-offer can never reach more workers than the original `dispatch_max_workers`, and never a worker who was not offered the task.
- A separate function instead of changing `eyes_release_claim`: 010 stays as verified. The gap between the two calls is harmless. If a YES claims the task in between, `eyes_reoffer` sees it is not `dispatched` and texts nobody.
- The releaser is excluded: they just said NO. Workers who said NO to the original offer without claiming are not recorded anywhere, so they are re-offered too.
- The release text goes first, so a failed `eyes_reoffer` call can never change what the releaser is told.
- Only `task_already_claimed` and `offer_invalid` delete the photo. `eyes_submit` raises both before inserting, so no submission can reference the photo. Any other error (database down) could come after a commit, so the photo is kept.
- `askEyes` is untouched. The offer fields are written out again in the NO path instead of being pulled into a shared helper, to keep engine changes to the two paths on the card.

## Assumptions
- Inkbox per-number limits (docs/vendor/inkbox.md, Limits). Re-offers go only to workers who texted START, which counts as messaging the line first. So the dedicated-line first-contact caps (10 per hour, 40 per 24 h) and the cold 1:1 rules (159 chars, no links, 3 messages before a reply) do not apply. The offer text is within them anyway (159 chars, no link, T1.3 tests). Against the 100 recipient sends per rolling 24 h per number, one release adds at most `dispatch_max_workers - 1` sends (2 by default), and every NO already costs one reply.
- Delivery on real Inkbox, not covered here: `createInkboxMessaging.sendOffer` sends with `idempotencyKey: offer:<task_id>:<phone>`, and the SDK adds `Prefer: idempotency-replay`. A re-offer to the same worker for the same task reuses that key, so Inkbox most likely replays the first send instead of delivering a new text. The retention window is not documented, and T1.3 lists "idempotency key limits" as not live-checked. The engine and fake messaging are correct, but production delivery needs the one-line `packages/comms` change in Known gaps. That package is not owned by this task.

## Verification
- `engine.int.test.ts` "a released task is offered again to idle workers...": the task is offered to the releaser, an idle worker and a busy worker (`workers_notified` 3). The busy worker then claims a newer task elsewhere, the releaser claims, and the idle worker receives a newer open offer. The releaser's NO produces exactly one offer text, to the idle worker (task id, `distance_m` 100). Nothing goes to the busy worker or the releaser. The idle worker's YES then gets the capture link for the released task, and the task is `claimed`.
- `engine.adversarial.int.test.ts` "a capture that loses to a NO during verification...": the worker's NO runs inside `verifySubmission`. With a photo, the capture is refused with `task_already_claimed`, the task is `dispatched` and fake storage is empty. Without a photo, the capture is refused the same way and nothing is deleted. `deletePhoto` is called exactly once across both cases.
- Fail on the old code: with `index.ts` from origin/main, both tests fail ("expected [] to deeply equal [ { to: ... } ]"; "expected deletePhoto to be called once, but got 0 times").
- Mutations, each fails the re-offer test and restoring 013 passes: no `sent_at` bump (select only), so the idle worker's YES claims the newer task; no idle rule, so the busy worker is texted; no releaser exclusion, so the releaser is texted. Dropping the `photo_url` guard fails the photo test (called 2 times).
- On `eyes_t418` a fresh role has no EXECUTE on `eyes_reoffer(uuid,uuid,timestamptz)`, and `proacl` is `{postgres=X/postgres}`.
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t418 pnpm test:integration` on a freshly created database (001 to 011 and 013 applied by `migrate`): 7 files, 90 tests pass.
- `pnpm verify:fast`: pass (lint, typecheck, 498 unit, 11 contract, 139 safety, intent check).
- Live-verified: no (texting is simulated on the deployed server).

## Known gaps
- Production delivery of re-offers needs, in `packages/comms/src/inkbox.ts`, `sendOffer: (to, offer) => send(to, offerText(offer))` (and `idempotencyKey: undefined` for the offer row in `inkbox.test.ts`). Without an explicit key the SDK makes one per call and reuses it for its own retries, so one send still cannot double-text. `askEyes` sends offers only when `eyes_post_task` created the task, so an `ask_eyes` retry never re-sends.
- A worker who cycles YES and NO texts the other offered workers again on every NO (at most `dispatch_max_workers - 1` each time). HELP and unrecognized replies already answer every inbound text, so one texter could already spend the per-number cap.
