## Why
#62, the two findings deferred from the PR #61 verdict. When a worker replies NO after YES the task goes back to `dispatched`, but the other offered workers were told "already claimed" and nobody tells them it reopened, so the agent waits for a YES that never comes. And a NO that lands while the vision judge runs makes `eyes_submit` refuse the capture after the photo was uploaded, leaving a public photo that no submission row points to.

## What
- `013_reoffer.sql`: `eyes_reoffer(task, released_by, now)` sets `sent_at = now` on the task's existing offer rows for workers who are opted in, available and idle (the 006 rule: no `claimed` or `submitted` task), excluding the releaser and any offer already re-sent (`o.sent_at = t.created_at`), only while the task is `dispatched` and before its deadline. It returns those workers. EXECUTE revoked from PUBLIC, anon and authenticated, as in 010 and 011.
- `handleWorkerReply` NO: after the release text, calls `eyes_reoffer` and sends each returned worker the same offer through `Messaging.sendOffer` (distance from `distanceMeters`), with `Promise.allSettled` like `askEyes`. A NO with nothing to release is unchanged.
- `createInkboxMessaging.sendOffer` no longer passes the fixed idempotency key `offer:<task_id>:<phone>`, so Inkbox delivers a re-offer instead of replaying the first send.
- `submitCapture`: when `eyes_submit` raises `task_already_claimed` or `offer_invalid` and a photo was uploaded (and not already deleted for faces), the stored photo is deleted. A failed delete logs `photo delete for task <id> failed` only. The original error is rethrown, so the worker sees exactly what they saw before.

## Decisions & alternatives rejected
- Migration 013 is needed for two reasons. Who was offered a task lives only in `offers`, and no RPC returns it (the engine reaches the database only through RPCs, InsForge in production). And `eyes_claim` claims the worker's newest `dispatched` offer by `sent_at`: without the bump, a worker holding a newer open offer would answer the re-sent text with YES and claim the other task. The test covers this case.
- No new offer rows: the existing rows are the original recipients, so the re-offer can never reach more workers than the original `dispatch_max_workers`, and never a worker who was not offered the task.
- Each worker is re-offered at most once per task (verifier finding on PR #66). Without a limit, a worker cycling YES and NO made Eyes text every other offered worker on each NO: 25 cycles spent the 100 sends per 24 h of the number on texts to other people. `eyes_post_task` inserts offers with `sent_at = p_now = tasks.created_at` (002), and the bump moves `sent_at` past it, so a bumped row never matches again. A task therefore causes at most `dispatch_max_workers - 1` re-offers in total. Real time always moves between posting and a release (a claim comes in between); tests with the fixed fake clock advance it before the NO.
- A separate function instead of changing `eyes_release_claim`: 010 stays as verified. The gap between the two calls is harmless. If a YES claims the task in between, `eyes_reoffer` sees it is not `dispatched` and texts nobody.
- The releaser is excluded: they just said NO. Workers who said NO to the original offer without claiming are not recorded anywhere, so they are re-offered too.
- The release text goes first, so a failed `eyes_reoffer` call can never change what the releaser is told.
- Only `task_already_claimed` and `offer_invalid` delete the photo. `eyes_submit` raises both before inserting, so no submission can reference the photo. Any other error (database down) could come after a commit, so the photo is kept.
- Offers are sent without our own idempotency key (approved by the coordinator on PR #66). The SDK sends `Idempotency-Key` with `Prefer: idempotency-replay`, so reusing `offer:<task_id>:<phone>` would make Inkbox replay the first send to that worker, and the re-offer would never arrive. Without our key, the SDK makes a new key per call and reuses it only for its own bounded retries (`dist/message_sends.js` `postMessage`), so one send still cannot double-text. `askEyes` sends offers only when `eyes_post_task` created the task, so an `ask_eyes` retry never re-sends. The other keys (capture, paid) are unchanged. A key that included `sent_at` was rejected: `OfferMessage` is a frozen contract and has no such field.
- `askEyes` is untouched. The offer fields are written out again in the NO path instead of being pulled into a shared helper, to keep engine changes to the two paths on the card.

## Assumptions
- Inkbox per-number limits (docs/vendor/inkbox.md, Limits). Re-offers go only to workers who texted START, which counts as messaging the line first. So the dedicated-line first-contact caps (10 per hour, 40 per 24 h) and the cold 1:1 rules (159 chars, no links, 3 messages before a reply) do not apply. The offer text is within them anyway (159 chars, no link, T1.3 tests). Against the 100 recipient sends per rolling 24 h per number, one release adds at most `dispatch_max_workers - 1` sends (2 by default), and every NO already costs one reply.
- Inkbox replays a send whose `Idempotency-Key` it has already seen. The SDK sends every iMessage with `Prefer: idempotency-replay` (`@inkbox/sdk` 0.7.19 `dist/message_sends.js`). Its README says a reused key returns the original result and does not send again; that is written for Slack sends, and I assume iMessage behaves the same. How long it keeps keys is not documented. T1.3 lists "idempotency key limits" as not live-checked.

## Verification
- `engine.int.test.ts` "a released task is offered again to idle workers...": the task is offered to the releaser, an idle worker and a busy worker (`workers_notified` 3). The busy worker then claims a newer task elsewhere, the releaser claims, and the idle worker receives a newer open offer. The releaser's NO produces exactly one offer text, to the idle worker (task id, `distance_m` 100). Nothing goes to the busy worker or the releaser. The idle worker's YES then gets the capture link for the released task, and the task is `claimed`.
- `engine.adversarial.int.test.ts` "a capture that loses to a NO during verification...": the worker's NO runs inside `verifySubmission`. With a photo, the capture is refused with `task_already_claimed`, the task is `dispatched` and fake storage is empty. Without a photo, the capture is refused the same way and nothing is deleted. `deletePhoto` is called exactly once across both cases.
- `inkbox.test.ts` "delivers a second offer for the same task to the same worker...": a stubbed identity that replays any key it has seen (and makes a fresh key when none is given, as the SDK does). Two `sendOffer` calls for the same task and phone deliver two texts. With `inkbox.ts` from origin/main the second call is replayed ("expected { id: 'im_1' } to deeply equal { id: 'im_2' }"). The template test now expects `idempotencyKey: undefined` for the offer.
- `engine.int.test.ts` "offers a released task again to each worker at most once...": the releaser claims and releases twice. The other worker gets the original offer and exactly one re-offer (2 offer texts), and the releaser only the original. Without `o.sent_at = t.created_at` it fails ("expected [...] to have a length of 2 but got 3"). Restoring 013 passes.
- Fail on the old code: with `index.ts` from origin/main, both engine tests fail ("expected [] to deeply equal [ { to: ... } ]"; "expected deletePhoto to be called once, but got 0 times").
- Mutations, each fails the re-offer test and restoring 013 passes: no `sent_at` bump (select only), so the idle worker's YES claims the newer task; no idle rule, so the busy worker is texted; no releaser exclusion, so the releaser is texted. Dropping the `photo_url` guard fails the photo test (called 2 times).
- On `eyes_t418` a fresh role has no EXECUTE on `eyes_reoffer(uuid,uuid,timestamptz)`, and `proacl` is `{postgres=X/postgres}`.
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t418 pnpm test:integration` on a freshly created database (001 to 013 applied by `migrate`, after merging main with 012): 7 files, 94 tests pass.
- `pnpm verify:fast`: pass (lint, typecheck, 503 unit, 11 contract, 139 safety, intent check).

## Known gaps
- A re-offered worker gets the same offer text a second time. The text cannot say that the task reopened, because `OfferMessage` and the templates stay as they are.
- `eyes_reoffer` bumps `sent_at` before the texts go out, and `Promise.allSettled` drops failed sends. A worker whose re-offer failed (Inkbox 429 or 5xx) has the released task as their newest offer without having its text, so their next YES, meant for the newest text they did get, claims the released task. `askEyes` already behaves this way (`eyes_post_task` inserts offer rows before sending); this is a second path of the same kind. Fix if it matters: bump only for workers whose send succeeded.
- A worker who cycles YES and NO still gets a reply to each of their own texts, as before this task. Other workers are re-offered at most once per task.
