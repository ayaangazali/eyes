## Why
A stranger who gets an Eyes text and types the domain landed on a developer page with nothing for humans: no idea what Eyes is, no way to join, no way to stop the texts (UX 10). The JOIN success screen only showed the START number when it was baked into the worker build, so a worker could not finish onboarding (UX 9). The top-up return pages looked like a different product and never said what was charged (UX 13, 24). PR #37 left the signup/join throttle key unbounded and its separate budgets unpinned. Nothing stopped a live Stripe key from running while Eyes was in test mode.
## What
- `GET /` is a human page first: "AI agents pay people nearby about $3 to check public places", a Join button to `config.worker_web_url`, a "Got a text from Eyes?" box (reply YES to claim, STOP to stop, START to resume, matching the engine's HELP text), the public-places rule, then the unchanged agent section (`POST /mcp` with Bearer, `POST /v1/signup`, llms.txt, openapi.json, agent-card.json, agents.md) and a link to `/status`. Server-rendered with `hono/html`, no JS.
- `GET /status` (new, HTML): each provider as "Texting: live" or "Texting: simulated" with one line on what it does, the database kind, and the deployed commit from `EYES_COMMIT` (first 12 chars) or "not recorded". It reads the same `liveProviders(env)` value and db kind as `/healthz`, now computed once per server; `/healthz` JSON is unchanged. The request log names it `/status`.
- `POST /w/join` returns `inkbox_number` from `INKBOX_PHONE_NUMBER` when the engine returns null or empty; an engine-provided number wins.
- Throttle key: right-most `X-Forwarded-For` entry, IPv4-mapped IPv6 (`::ffff:a.b.c.d`) keyed as its IPv4 address, other IPv6 keyed on its /64 (expanded, so `2001:db8::1` and `2001:0db8:0:0::2` share a bucket), anything else cut to 64 characters. The node adapter treats a blank `X-Forwarded-For` as absent and fills the socket address.
- One small dark header (amber eye mark from the dashboard, "Eyes" linking to `/`) on HOME, `/status`, the owner console, `/topup/done`, `/topup/cancel`, `/w/connect/done` and the payments error pages; payments pages share one `shell` with the owner console.
- `createTopupCheckout` adds `amount_cents` to the success URL it sends Stripe; `/topup/done?amount_cents=2000` says "$20.00 added to your agent's balance." (display only, 1-6 digits, anything else falls back to a generic line). Cancel says nothing was charged and to reopen the agent's top-up link. Both say "You can close this page."
- `createStripePayments` throws at startup for an `sk_live_` or `rk_live_` key unless `EYES_TEST_MODE` is exactly `"false"`, naming both fixes.
## Decisions & alternatives rejected
- Amount in our own success URL instead of `{CHECKOUT_SESSION_ID}` plus a Stripe lookup: no extra API call or failure mode, and the page is display only; the balance is credited only from the signed webhook. Built in the Stripe adapter because the engine (not owned) builds the base URL.
- No link to the owner console from `/topup/done`: the agent holds the top-up link, so linking the owner token there would hand it to the agent (ADR-011).
- HOME/status CSS lives in apps/mcp and the payments shell in packages/payments (two copies of about six brand rules) rather than importing page chrome from the payments package into the server's home page.
- IPv4-mapped handling is needed because grouping `::ffff:a.b.c.d` to its /64 would put every IPv4 client of a dual-stack listener in one bucket.
- `rk_live_` is refused too: a restricted live key moves real money the same way.
- `HTTP_ROUTES` (frozen, packages/core) is not edited. It should gain `status: "GET /status"` in a later ADR.
## Assumptions
- The JOIN page is served at the root of `config.worker_web_url` (apps/web/worker/index.html).
- Stripe keeps query parameters on `success_url` (docs/vendor/stripe.md shows a query on it).
- No deploy platform sets a commit variable for us (docs/vendor/mcp-use-manufact.md); `EYES_COMMIT` must be set at deploy, e.g. `--env EYES_COMMIT=$(git rev-parse --short HEAD)`.
