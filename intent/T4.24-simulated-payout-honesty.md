## Why
The deployed server runs `EYES_PROVIDERS=live` with real Inkbox texting and real Claude vision but no Stripe key, so payments are the fake provider while real people get the texts. On that configuration START sent "Set up payouts here: <link>" and the link redirected to `connect.fake.test`, which does not resolve; a worker with a fake account got "you've been paid $3" after a fake transfer, and one without got "Your $3.00 for this task is waiting"; offers, the capture page and the JOIN page all promised $3. None of it was true. The engine and comms could not tell a simulated payout from a real one, the same gap ADR-018 closed for owner email.

## What
- `AppConfig.live_payouts`, default `false` (ADR-022). `main.ts` and `scripts/resolve-task.ts` set it from `liveProviders(env).payments`.
- Engine, when false: START drops the payout link and says "This is a test server and payouts are simulated, so no real money is paid."; HELP, the not-signed-up reply and `opt_in_instructions` add that sentence; the capture result is "Verified." or the manual-check text plus that sentence; a verified answer from a worker with no payout account gets the paid notice instead of the payout-link text. `OfferMessage` and the `sendPaid` message carry `live_payouts`.
- Comms, when the message says false: offers start "Eyes test ($0):" with no amount; the paid notice says the answer was accepted and no money was sent because payouts are simulated. Place text still goes through `placeText`.
- Routes, when false: `/w/connect/<token>` answers a "Payouts are simulated" page without minting an onboarding link; the earnings page says its amounts are not real money and labels each payout "Simulated, nothing sent".
- Worker web: build-time `VITE_LIVE_PAYOUTS`. Unless it is `"true"`, the JOIN page shows a test-server notice and hides the "$3 through Stripe" sentence and the payout-link step, and the capture page shows "Test task, no real pay" and a plain "Verified" heading.
- Harnesses that run the payout flow with the fake provider as a stand-in for Stripe set `live_payouts: true`; the golden web build sets `VITE_LIVE_PAYOUTS=true`. DEPLOY says when to set the build flag.

## Decisions & alternatives rejected
- The flag rides on the two messages comms words (offer, paid) rather than on the provider or a `createInkboxMessaging` option: one source of truth (the config), visible in the fake outbox to integration tests.
- The paid notice stays `sendPaid`, not a `sendText` from the engine: keeps place sanitizing in comms and the `paid:<task>:<phone>` idempotency key.
- The money flow is unchanged (a fake transfer still marks the task paid): changing status or ledger would change agent tools and the ops feed for a wording fix.
- JOIN page uses a build flag, not wording true in both modes: the live pitch says "get paid", and only a notice on simulated builds keeps both true. The default (unset) is the simulated copy, so forgetting the flag under-promises.
- The simulated connect page does not call `workerConnectUrl`: no fake account, no onboarding link, no token check needed for a page that says the same thing to everyone.
- Offer prefix is "Eyes test ($0):" rather than "Eyes test (no real pay):": the longer prefix put the worst-case offer at 166 characters, over the 159-character cold-message limit the offer test enforces.

## Assumptions
- `liveProviders(env).payments` is exactly the switch that wires `createStripePayments` in `main.ts` (checked: same object, same key).
- The worker web on InsForge Sites is rebuilt from main after merge; until then it shows the old copy.

## Known gaps
- Link-preview meta tags (`og:title`, `og:description`) on the JOIN and capture pages still say "get paid"; crawlers read static HTML without scripts, so they cannot follow the build flag.
- The JOIN headline and intro still say "get paid", with the test-server notice directly below, the same pattern as HOME and `/status`.
- Agent-facing `await_answer` text for status `paid` still says "the worker is paid" on a simulated server; out of scope (agent-facing, not worker-facing).
