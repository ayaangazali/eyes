## Why
The ops dashboard was a secret URL: whoever had the link saw worker positions, and nobody knew who looked. Operators had no record of what the server did beyond one machine's process log. A worker whose answer was held in `needs_review` could only wait.

## What
- `/ops` (health, activity, money, workers, review queue, tickets, event log) and `/ops/live` need a signed session cookie (`__Host-eyes_ops`, HttpOnly, Secure, SameSite=Strict, 12 h). Sign-in at `/ops/login`: phone or email; if it is on `ops_allowlist` (migration 015 seeds only the placeholders +15555550100 and ops@example.com; real operators are added at `/ops/allowlist` or after an `EYES_OPS_KEY` break-glass sign-in) a 6-digit code goes out by Inkbox text or Primitive email. Same reply either way. Codes are stored as an HMAC, last 10 minutes and allow 5 guesses; 10 tries an hour per client IP (`cf-connecting-ip`) and per identifier. Every POST checks `Origin` against `EYES_PUBLIC_API_URL`. `/ops/allowlist` lists masked entries, adds a phone (E.164) or email, and refuses to remove yourself or the last entry. `EYES_OPS_KEY` stays as an optional break-glass link that signs the browser in.
- Event log (`events` table, migration 015): HTTP requests (path without query, token segments masked), service calls with agent id and outcome, webhooks, texts and emails (kind and task id only), safety and vision verdicts, payout attempts, logins, allowlist changes, console warnings and errors. Task, ledger and ticket rows come from triggers. The server redacts keys, tokens, phones and emails, batches writes every 2 s and keeps the last 500 in memory as the fallback when the database is down. `/ops/events` filters by kind, level, task id and text.
- Tickets: the held-answer text tells the worker to reply HELP. HELP within 48 h of a `needs_review` answer opens a ticket (or adds to the open one) and replies with its number; later free text adds to the open ticket; otherwise HELP keeps today's reply. The dashboard shows open tickets first with photo, checks, vision reason and distance. Release and Refund call `resolveTask` (the same call as `scripts/resolve-task.ts`), then `resolveTicket` closes the ticket and texts the worker; Resolve closes it with a note only. Every action needs a note and a second click.
- Privacy pages (worker and landing) say tickets keep the worker's message text.
- Optional ClickHouse (`CLICKHOUSE_URL`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE`, off when the URL is unset): every redacted event also goes to a ClickHouse `events` MergeTree (by `(kind, ts)`, monthly partitions, 180-day TTL) through batched `INSERT ... FORMAT JSONEachRow` over fetch, every 2 s or 500 rows, with a 10,000-row queue that drops the oldest (counted) and exponential backoff while ClickHouse is down. Task, ledger and ticket rows are copied from the Postgres triggers every 2 s. Materialized views: requests per minute by route and status, p50/p95 latency per route, calls per hour by outcome, task transitions per hour. `scripts/clickhouse-migrate.ts` applies `packages/db/clickhouse/*.sql`. The dashboard's Trends panel (`/ops/series`: requests/min, 5xx rate, p95 latency over 2 h; tasks per hour by status and payouts per hour over 24 h) reads ClickHouse, or the Postgres feed and the memory ring without it, drawn as plain SVG.

## Decisions & alternatives rejected
- Ops pages send `Referrer-Policy: same-origin`, not `no-referrer`: under `no-referrer` browsers send `Origin: null` on the page's own fetch POSTs, so the Origin check would reject every button.
- Triggers for task, ledger and ticket events, so no code path can skip them; the app logs the rest.
- ClickHouse over its HTTP interface with `fetch`, not a client library: one insert format and one query format are all the dashboard needs.
- The trigger-event mirror starts at the newest row instead of backfilling: its cursor is not persisted, so a backfill would duplicate rows on every restart (`ponytail:` note, with the 500-rows-per-tick ceiling).
- Rate limits are in memory per process (`ponytail:` note): Eyes runs one server process.
- No event pruning yet (`ponytail:` note in migration 015).
- Ticket column is `note` (the operator's resolution note), as the task spec names it.

## Assumptions
- Requests reach the server through the Cloudflare proxy, so `cf-connecting-ip` is the client IP. A direct hit on the origin could set it; that would only spread a rate limit, never skip sign-in.
