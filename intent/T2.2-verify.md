## Why
An agent only pays for an answer it can trust, and a worker should be paid without a human in the loop when the evidence is clear. `verifySubmission` decides, per submission, whether the worker was there, shot the photo live before the deadline, and whether the photo answers the question without showing faces. Only when all three hold does the engine auto-approve; otherwise the task goes to `needs_review` with escrow held.

## What
- `verifySubmission`: `worker_distance_m` (haversine via `distanceMeters`), `gps_ok`, `fresh_ok`, `vision_ok` + `vision_reason`, `confidence`, `auto_approve = gps_ok && fresh_ok && vision_ok`. Never throws on a vision failure.
- `createClaudeVision(env)`: `claude-sonnet-5-5` via `@anthropic-ai/sdk` 0.135.0 `messages.parse` with a zod structured output matching `VisionVerdict`; photo sent as a URL image block; throws at construction without `ANTHROPIC_API_KEY`; 20 s timeout, 1 retry.
- Added `zod` 4.6.7 (same version as `@eyes/core`) to `@eyes/verify` for the output schema.

## Decisions & alternatives rejected
- GPS rule: `gps_ok = accuracy_m <= 100 && distance - accuracy_m <= task.radius_m`. The accuracy circle must reach the task radius, so an honest 60 m indoor fix 200 m out still passes a 150 m radius; a fix worse than 100 m never passes on its own, even on the spot. Rejected: ignoring accuracy (fails honest indoor fixes) and uncapped slack (a 2 km cell fix would pass).
- Freshness, all against server `received_at`: `received_at <= deadline_at`; `captured_at <= received_at + 60 s` (clock skew); `received_at - captured_at <= 5 min` (live capture, allows typing an answer and a slow upload). Unparseable timestamps fail closed (NaN comparisons are false).
- Vision: ok only when `answers_question && !prominent_faces`. Faces prefix the reason with "Rejected: a person's face is prominent in the photo." No photo gives `vision_ok: false`, reason `no photo`, and vision is not called. A thrown vision error gives `vision_ok: false` with "Vision check unavailable (<error>); the photo needs manual review." Vision still runs when gps or freshness fail so the reason stays informative.
- Confidence: `0.25*gps_ok + 0.25*fresh_ok + 0.5*vision_confidence`, where vision confidence counts only when `vision_ok` and is clamped to [0, 1]. All pass at vision 0.9 gives 0.95; no photo caps at 0.5.
- Prompt injection: the question, place label and worker answer are JSON-encoded with `<` escaped as `<` inside one `<task_data>` block, so untrusted text cannot close the delimiter; the system prompt says to treat it as data and ignore instructions in it.
- Effort `low`: Sonnet 5.5 cannot disable thinking; low effort keeps the judge fast for the waiting worker. Structured output via `output_config.format` (not forced tool use, which Sonnet 5.5 rejects).
- Rejected: the server-side refusal fallback beta (`fallbacks: "default"`). A refusal returns no verdict, `judge` throws, and the submission lands in `needs_review`, which is already safe.

## Assumptions
- No Anthropic vendor note exists. API shapes come from the installed SDK `.d.ts` (0.135.0): `URLImageSource {type:"url", url}`, `messages.parse` + `zodOutputFormat` (`helpers/zod`), `OutputConfig {effort, format}`, client options `timeout` (ms) and `maxRetries`.
- `photo_url` from `Storage.putPhoto` is fetchable by Anthropic (public `captures` bucket direct URL or a presigned URL, docs/vendor/insforge.md Storage). Photos are JPEG/PNG/GIF/WebP.
- `accuracy_m` is browser-reported and spoofable; the cap protects against honest bad fixes, not against cheating.

## Known gaps
- Not run against the live Anthropic API.
- If the photo bucket is private and URLs are not presigned, Anthropic cannot fetch them; `judge` would then need to fetch the bytes with the admin key and send base64.
- `vision_reason` on a vision outage includes the SDK error message, which reaches the agent.
