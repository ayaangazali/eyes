- [minor] packages/db/migrations/013_reoffer.sql:3 + packages/engine/src/index.ts:766: nothing limits re-offers per task or per hour. Each NO that releases a claim sends the offer again to every idle worker who was offered the task. A worker can make Eyes text other people repeatedly. Before this PR, a texter could only make Eyes reply to themselves. Repro (scratch int test, real Postgres, default config): A cycles YES/NO 10 times. In 205 ms of engine time, B and C each receive the identical offer 10 times: 20 inbound texts produce 40 outbound (10 capture links, 10 "released" texts, 20 offers). Each YES/NO pair costs 4 sends, so 25 pairs (50 inbound texts) use up Inkbox's 100 recipient sends per rolling 24 h per number (docs/vendor/inkbox.md:147). Before this PR that took about 100 inbound texts (HELP/unknown). dispatch_max_workers is code-only config (default 3, no env mapping). At 10, 20 inbound texts produced 110 outbound (90 offers), over the daily cap in one burst. I rated it minor because a single texter could already reach the cap, and the default amplification is 2x. The intent lists this under Known gaps, but its reasoning misses that the extra texts go to other people. Suggested fix: re-offer each worker at most once per task by adding `and o.sent_at = t.created_at` to 013. 002:147-148 inserts offers with sent_at = p_now = tasks.created_at, so a bumped row is never bumped again. That caps a task at dispatch_max_workers - 1 re-offers in total.
- [minor] packages/engine/src/index.ts:766-783: eyes_reoffer bumps sent_at before the send, and Promise.allSettled drops failures. If a re-offer send fails (Inkbox 429/5xx), that worker's newest offer is now the released task, which they never got a text for. Their next YES, meant for the newest text they did receive, claims the released task instead. Repro (scratch test V66DIVERT): W is offered X, then a newer Y. A claims X. sendOffer is stubbed to throw while A replies NO. W replies YES: W's last offer text was Y, but W claimed X. askEyes already behaves this way (eyes_post_task inserts offer rows before sending), so the PR adds a second path, not a new kind of problem. Suggested fix: deferrable. Either bump sent_at only for recipients whose send succeeded, or accept this like the askEyes case and record it under Known gaps.
- [minor] docs/vendor/inkbox.md:69,153: the docs still say to use a `taskId:workerId` key "so dispatch retries never double-text" and to "always pass idempotencyKey". The PR removes the offer key, so the vendor doc now contradicts inkbox.ts:153. Suggested fix: change both lines to say offers rely on the SDK's per-call key (fixed keys are kept for capture and paid texts).
