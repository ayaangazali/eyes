- [minor] packages/payments/src/index.ts:118-119: the check ignores the `Stripe-Should-Retry` header. A 400, 402 or 404 that carries `Stripe-Should-Retry: true` is still tagged definite. Stripe sends that header only when a retry with the same key could get a different answer, which means the result was not saved under the key. That removes the premise in ADR-012 that makes [timeout, 400] safe ("Stripe saves a 400, 402 or 404 under the key and replays it to any earlier try"). stripe-node retries on that header, so the reachable sequences `net,400r`, `to,400r`, `502h,400r,400r` and so on all come back DEFINITE in M3. N2 shows the double pay that follows if a late try 1 then runs. This is not a blocker: no documented Stripe 400/402/404 carries should-retry true. The one known transient 400 (code rate_limit) becomes StripeRateLimitError and is already tagged unknown. Repro: v57r3-attack M3 row `net,400r` gives DEFINITE; N2 (try 1 runs late, try 2's 400 not saved) gives 2 transfers. Suggested fix: add `&& (err as { headers?: Record<string, string> }).headers?.["stripe-should-retry"] !== "true"` to `refused`. stripe-node puts the response headers on the error (Error.js:84, RequestSender.js:118).

- Corner "network error, then 400" against Stripe's idempotency rules: try 1 cannot create a transfer after try 2 got an endpoint 400 under the same key. There are three cases:
  - Try 1 finished first. Try 2 replays try 1's saved result, so it would get 200 if a transfer was made. A 400 therefore means try 1 made none.
  - Try 1 is still running when try 2 arrives. Try 2 gets 409 (in progress), not 400.
  - Try 1 arrives after try 2. Try 2's endpoint 400 is saved under K1 and try 1 gets it replayed. N1 models this: K1 has a saved 400 after 2 tries, the lease is released, the webhook pays under K2, and try 1 runs 3 s late and gets the replay. Final count: 1 transfer, 1 payout.
  - A validation 400 is not saved, but it depends only on the request body, and every try sends the identical body (RequestSender reuses requestData). So try 1 fails validation too.
  - 409 then 400 follows the same reasoning. The 409 is a replay or an in-progress conflict, and any 400 after it is the saved result.
