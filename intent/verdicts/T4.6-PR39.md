- [minor] packages/db/migrations/006_dispatch_idle_workers.sql:23-36: the new `already_yours` guard has a check-then-act gap. Under READ COMMITTED each plpgsql statement takes a fresh snapshot. If a worker's first YES commits between the second YES's guard select (line 27) and its open-offer select (line 36), the second YES skips the now-claimed newer offer and claims the older open one, so the worker holds two `claimed` tasks. This needs two open offers (allowed by design, see intent "Decisions") and two YES from one phone within about a millisecond. ADR-010: deferrable. It hardens a path that already has a guard, it is not a regression (on main a plain sequential double YES claims both, and 1/100 concurrent pairs did), and escrow still refunds on expiry. Repro: in a scratch DB, copy `eyes_claim` as `eyes_claim_slow` with `perform pg_sleep(0.3)` before the offer select. Session 1 runs `begin; select eyes_claim(W, now())` (claims the newer offer), waits 150 ms, then commits. Session 2 starts `eyes_claim_slow(W, now())` 30 ms after session 1. Result: `won,won`, worker holds 2 claims. Without the injected sleep: 0/300 on the PR. Suggested fix: replace the line-23 existence check with `perform 1 from workers where id = p_worker_id and opted_in and available for update; if not found then return; end if;`, which serialises one worker's claims (verified: same forced interleaving gives `won,already_yours`, 1 claim). Open a follow-up issue and add it to Known gaps per ADR-010.
