- [blocker] packages/payments/src/index.ts:119-120 (with the ADR-012 addendum lines 47-48): the classifier looks only at the status of the last response, but one `transfers.create` call is up to 3 tries with the same Idempotency-Key. Stripe returns a 429 before its idempotency layer runs, so a 429 on a retry says nothing about the earlier tries. In the sequence [try 1: timeout, connection error or 5xx that Stripe still runs, try 2: 429], the error is tagged as a refusal and the lease is released. The next trigger mints K2, and its lookup is empty while try 1 is still running, so a second transfer is made. This is the round-1 S2b class (Stripe runs the POST seconds after the client gave up), not S6. The fix closed it only for the case where all 3 tries fail without a response. The two failures are likely to come together: stripe-node retries 0.5 s after a timeout, which is exactly when Stripe is slow and its rate, concurrency and lock limiters return 429. Judgement on a 429 by itself: it is a definite refusal, because a rate-limited request is not executed and stripe-node does not retry a 429 unless the response carries `Stripe-Should-Retry: true` (RequestSender.js:200-220). Releasing would be right for a lone 429, but payoutWorker cannot tell a lone 429 from one on a retry. Repro: scratchpad/v57r2-attack.int.test.ts, test S8. Try 1 throws a network error and the fake Stripe runs it 4 s later; try 2 gets 429 rate_limit_error. A capture on an active account leaves release.stripe_ref null (released). An immediate B.markWorkerOnboarded(acct) pays under a second key. 4.5 s later there are 2 transfers in `task_<id>` and 1 payout row. S8c (429 lock_timeout with Stripe-Should-Retry: true, 3 tries) gives the same 2 transfers. In the classification matrix, "MIXED timeout then 429" and "MIXED 503 then 429" both come back with outcome_unknown false. Suggested fix: treat only endpoint refusals as definite (`[400, 402, 404].includes(status) && err.type !== "StripeRateLimitError"`), because Stripe saves those under the key and replays them to an earlier try of the same key. Tag everything else outcome_unknown (429 and 401/403 too), and add a [timeout, 429] row to the unit table at index.test.ts:444.
