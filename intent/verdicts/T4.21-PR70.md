- [minor] intent/decisions/ADR-021-join-oracle.md:21 (Consequences) and intent/T4.21-sweep2.md:40 (Known gaps): the timing note has the wrong direction and is about 3x too small. ADR says the conflict path "runs one more indexed select than an insert, so the response time differs by well under a millisecond". Measured on the PR head with fake providers and local Postgres, 50 interleaved samples per class, unique X-Forwarded-For per request: a KNOWN phone answers FASTER, not slower. known p10/p50/p90 = 0.68/0.89/1.93 ms, fresh = 1.73/2.36/4.35 ms (first run: medians 1.09 vs 2.35 ms). A one-request classifier at the midpoint is 92% accurate on loopback. Cause: a fresh join commits an INSERT, which flushes WAL. A known phone hits `on conflict do nothing`, which inserts nothing and writes nothing. The gap is likely larger on a hosted DB with networked fsync. Limits on it: each probe of an unknown phone enrolls that phone, so an attacker gets one sample per phone and leaves a workers row behind; internet jitter adds noise; the throttle still applies, though X-Forwarded-For spoofing gets around it (first sweep #2). The body oracle this PR targets is closed. This is a residual side channel, and the decision record describes it wrongly. Repro: run the API on the PR head, POST /w/join 50 times with one phone that has already joined and 50 times with new phones, interleaved, each with a unique X-Forwarded-For, then compare medians. Suggested fix: change the ADR-021 Consequences line and the T4.21 Known gaps line to "a known phone answers ~1.5 ms faster (no INSERT/WAL flush), single-shot distinguishable on loopback", and file a follow-up. A real fix needs a migration or response padding, which is out of scope here.
