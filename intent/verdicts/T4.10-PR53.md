- [minor] apps/mcp/src/main.ts:59-60 + packages/core/src/fakes.ts:15,83-85: this PR adds a new sink: the owner link is emailed to `payer_email` taken from the webhook. On the real Stripe path that address is signature-verified and safe. In fake payments mode the "signature" is the constant `fake-signature`, published in a public repo, and the fake parser passes attacker JSON through unchanged. `liveProviders` lets each provider go live on its own key, so a server with `EYES_PROVIDERS=live`, `PRIMITIVE_API_KEY` set and no `STRIPE_SECRET_KEY` turns a forged webhook into an owner-link email to an attacker's address. The agent knows its own `agent_id` from the signup output (packages/engine/src/index.ts:344), so this brings back the exact self-ownership hole from #38, for any agent whose id is known. The current deploy cannot be exploited this way because email is fake (in-memory outbox, never logged, no route reads it), and the PLAN §4 order puts Stripe before Primitive. That is why this is non-blocking under ADR-010. Repro (local only, never against the live server): start with EYES_PROVIDERS=live, PRIMITIVE_* set and STRIPE_* unset, then `POST /webhooks/stripe` with header `stripe-signature: fake-signature` and body `{"type":"topup.completed","agent_id":"<id>","amount_cents":100,"ref":"x","payer_email":"<attacker>"}`. Primitive then sends the p: link to the attacker. Suggested fix: in main.ts, `if (live.email && !live.payments) exit("live email needs live Stripe: a fake-signed webhook could email owner links")`. Land it before PRIMITIVE_API_KEY goes on the server.
- [minor] packages/engine/src/index.ts:542-555 / intent/decisions/ADR-015-owner-link-to-payer.md (Consequences): every payer gets permanent owner control, and the payer does not have to be the agent. The `t:` top-up link appears in agent-visible output (signup, get_balance, insufficient_balance), and agents are told to pass it on. So anyone who obtains it and pays the minimum top-up gets the `p:` link. With it they can raise limits on a balance someone else funded, freeze the agent, and read the last 20 tasks and 50 ledger rows. ADR-015 only discusses an agent paying with its own card ("its own money"). This matches the accepted ADR, so it is not an implementation defect, but the escalation from a `t:` holder to owner is not recorded. Repro: from signup take the agent's topup_url, complete Checkout in a different browser with the payer email set to Y, and Y receives a working /owner/<token>. Suggested fix: the orchestrator records this escalation in the ADR-015 Consequences, or narrows delivery later (for example, first top-up only).
