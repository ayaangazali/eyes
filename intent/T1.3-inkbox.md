## Why
Eyes reaches workers by text. The engine decides who gets an offer and who wins a claim; this package owns the wording, the Inkbox calls and the inbound webhook, so a worker's "YES" becomes `handleWorkerReply` only when Inkbox really sent it, and no agent can put a link or phone number on a stranger's phone.
## What
- `createInkboxMessaging(env)`: SDK client from `INKBOX_API_KEY`, identity from `INKBOX_AGENT_HANDLE` (fetched lazily once, refetched after a failure); throws at construction if either is missing. All sends use `identity.sendText`; offer, capture and paid carry idempotency key `<kind>:<task_id>:<phone>`.
- Pure, exported templates. Cold offer: bounty, a fixed phrase per `task_type`, place, rough distance, "Reply YES to claim"; never the agent's question (shown only on the capture page after a claim). Capture link: URL, place, deadline in Pacific time, no-faces rule.
- Every template passes `place_label` through one whitelist: NFKC, drop format chars, first comma segment, keep only tokens made of letters, marks, digits, `'`, `&`, `-` with no 3+ digit run, drop all digit tokens if more than 4 digits survive, whole tokens up to 40 chars, else "a nearby place".
- `parseReplyIntent`: NFKC, lowercase, tokens of letters/digits, 👍 and `?`. All-yes words (incl. "yes 👍", "👍👍") claim; other intents match the whole phrase ("opt out", "stop texting me"). A `?` turns yes/no/start into unknown, so "y?" never claims.
- `inkboxRoutes`: HMAC over the exact raw bytes, optional bearer, 300 s window; `text.received` and 1:1 `imessage.received` from an E.164 sender go to `handleWorkerReply`. Other events, malformed or non-E.164 bodies: 200 "ignored". Service errors: logged as error name/`EyesError` code, event id and the phone's last 4 digits, answered 200.
- `scripts/send-test.ts <phone> [text]` for the first live send.
## Decisions & alternatives rejected
- Orchestrator ruling (PR #1 security review, ADR-005): no agent free text in the cold offer. Rejected: scrubbing the question, because IDN domains, fullwidth dots, zero-width splits and spelled-out numbers cannot all be filtered. The place label stays, so it gets a whitelist rather than a blacklist.
- SDK `verifyWebhook` (owns `whsec_` prefix handling) in a try/catch because it throws on a wrong-length signature; the documented 300 s window is our own check. Bearer compare is constant-time via SHA-256 digests.
- Await the service before answering: Inkbox only logs the status, and this keeps the work inside the request on any host (ADR-004 fallback).
- Group iMessages and tapbacks ignored: a reaction cannot say which offer it answers.
## Assumptions
- Signing per docs/vendor/inkbox.md and https://inkbox.ai/docs/api/phone/webhooks.md (headers, `{id}.{ts}.{raw_body}`, 300 s). Payload shapes from the SDK's webhook types and docs samples, not yet a live delivery.
## Verification
- `packages/comms/src/inkbox.test.ts`, 110 unit tests, no network (SDK mocked with `vi.mock`, `verifyWebhook` real). Webhook: docs-shaped SMS/iMessage replies reach the service; a non-UTF-8 body signed over bytes is accepted; 401 for wrong key, tampered body, stale/future timestamp, short signature, each missing header, empty signing key, wrong bearer; 200 "ignored" with no body logged for 11 ignored or malformed bodies; failure logs carry no message, body or full phone. Messaging: env guard, each method's template and idempotency key, one identity fetch for concurrent sends, refetch after failure, SDK errors propagate. Templates: 23 adversarial place labels across all four templates, offer never contains the question and stays at or under 159 chars for every task type. 47-row intent table.
- 23 mutations (signature, window, bearer, key guard, raw bytes, group filter, each whitelist step, identity memo and reset, keys, apiKey, NFKC, `?` rule, log content, cents, phrases) each fail a test. `pnpm verify:fast`: pass. Live-verified: no (no Inkbox key yet).
- Verifier verdicts: round 1 intent PASS, spec FAIL, security FAIL, test FAIL; round 2 security+spec PASS, test PASS (intent/verdicts/T1.3-PR1.md). CI green on PR #1.

## Known gaps
- Webhook latency equals service latency, since the handler awaits `handleWorkerReply`.
- No dedupe on event `id` (needs engine-owned storage); a retried YES is harmless, other retried replies are processed twice.
- Deadline time zone is fixed to America/Los_Angeles; the contract has no worker time zone.
- Not live-checked: payload shape, whether START arrives as `text.received`, idempotency key limits.
