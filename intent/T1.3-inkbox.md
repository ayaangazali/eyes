## Why
Eyes reaches workers by text. The engine decides who gets an offer and who wins a claim; this package owns the wording, the Inkbox calls and the inbound webhook, so a worker's "YES" becomes `handleWorkerReply` only when Inkbox really sent it, and no agent can put a link or phone number on a stranger's phone.
## What
- `createInkboxMessaging(env)`: SDK client from `INKBOX_API_KEY`, identity from `INKBOX_AGENT_HANDLE` (fetched lazily once, refetched after a failure); throws at construction if either is missing. All sends use `identity.sendIMessage({ to, text, idempotencyKey })` on the identity's iMessage line (the SDK sends the key as `Idempotency-Key`); offer, capture and paid carry `<kind>:<task_id>:<phone>`. A send answered with status `error` or `declined` throws with Inkbox's error code instead of passing as delivered.
- Pure, exported templates. Cold offer: bounty, a fixed phrase per `task_type`, place, rough distance, "Reply YES to claim"; never the agent's question (shown only on the capture page after a claim). Capture link: URL, place, deadline in Pacific time, no-faces rule.
- Every template passes `place_label` through one whitelist: NFKC, drop format chars, first comma segment, keep only tokens made of Latin-script letters, marks, digits, `'`, `&`, `-` that contain at least one letter or digit and no 3+ digit run, drop all digit tokens if more than 4 digits survive, whole tokens up to 40 chars, else "a nearby place".
- `parseReplyIntent`: NFKC, lowercase, tokens of letters/digits, 👍 and `?`. A reply whose every word has the same intent takes it ("yes 👍", "👍👍", "STOP STOP"); otherwise the whole phrase must match ("opt out", "please stop", "stop all", "stop texting me"). A `?` turns yes/no/start into unknown, so "y?" never claims. Lookups use `Object.hasOwn`, so words like "constructor" are unknown instead of resolving to `Object.prototype` members (fix shipped in the T3.1 PR).
- `inkboxRoutes`: rejects a signing key that is empty after stripping `whsec_`, then HMAC over the exact raw bytes, optional bearer, 300 s window; `text.received` and 1:1 `imessage.received` from an E.164 sender go to `handleWorkerReply`. Other events, malformed or non-E.164 bodies: 200 "ignored". Service errors: logged as error name/`EyesError` code, event id and the phone's last 4 digits, answered 200.
- `scripts/send-test.ts <phone> [text]` for the first live send; it goes through `createInkboxMessaging`, so it uses the iMessage path too.
## Decisions & alternatives rejected
- Orchestrator ruling (PR #1 security review, ADR-005): no agent free text in the cold offer. Rejected: scrubbing the question, because IDN domains, fullwidth dots, zero-width splits and spelled-out numbers cannot all be filtered. The place label stays, so it gets a whitelist rather than a blacklist.
- SDK `verifyWebhook` (owns `whsec_` prefix handling) in a try/catch because it throws on a wrong-length signature; the documented 300 s window is our own check. Bearer compare is constant-time via SHA-256 digests.
- Await the service before answering: Inkbox only logs the status, and this keeps the work inside the request on any host (ADR-004 fallback).
- Group iMessages and tapbacks ignored: a reaction cannot say which offer it answers.
- iMessage line instead of SMS (humans' choice for cost, docs/DEPLOY.md): one send path, `sendIMessage`, with no channel switch, since the SDK needs nothing else and the identity has no SMS number. Inbound already handled `imessage.received` (phone from `data.message.remote_number`, body from `content`) through the same signature check as `text.received`. The templates already met the cold iMessage rule (159 chars or fewer, no links or phone numbers before the worker replies); workers text START first, so the capture link after YES is allowed.
- Follow-up (PR #1 round 2 notes): place letters are Latin-script only, so homoglyph dots and digits from other scripts ("evilꓸcom", "ЧlƼ-ƼƼƼ-OlԳԳ") drop with their token. Non-Latin place names fall back to "a nearby place"; the full label is still on the capture page.
## Assumptions
- Signing per docs/vendor/inkbox.md and https://inkbox.ai/docs/api/phone/webhooks.md (headers, `{id}.{ts}.{raw_body}`, 300 s). Payload shapes from the SDK's webhook types and docs samples, not yet a live delivery.

## Known gaps
- Deferred (ADR-010): iMessage sent from an Apple ID email is now routed as a verified-email reply. E.164 senders keep the phone path; email replies use the existing DMARC-authenticated verification and worker identity flow.
- Webhook latency equals service latency, since the handler awaits `handleWorkerReply`.
- No dedupe on event `id` (needs engine-owned storage); a retried YES is harmless, other retried replies are processed twice.
- Deadline time zone is fixed to America/Los_Angeles; the contract has no worker time zone.
- Not live-checked: payload shape, whether START arrives as `imessage.received` or is consumed by Inkbox, idempotency key limits.
- iMessage line: workers must use iPhones (no SMS fallback without a phone number); a dedicated line may start at most 40 new conversations per 24 h; cold first messages stay limited to 159 chars with no links, phone numbers or media and at most 3 before a reply.
- If the Inkbox console gives a shared router number with a connect command instead of a dedicated line, each worker must text the connect command to the router before START, and the connection expires after 14 idle days (docs/vendor/inkbox.md, docs/DEPLOY.md).
