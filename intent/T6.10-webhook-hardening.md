## Why
A Checkout session created against another deployment (not this database) paid $20 in test mode. Crediting it failed the `ledger_agent_id_fkey` foreign key, the webhook route had no catch, and Stripe got a 500 and kept retrying. The first-payer owner email failed too, and the log recorded only `PrimitiveApiError`, which says nothing about the cause.

## What
- `POST /webhooks/stripe`: when `creditTopup` fails with `ledger_agent_id_fkey`, the route logs `stripe top-up for unknown agent <agent id first 8>, not credited (session <session id first 12>)` and returns 200. Every other credit error is rethrown and still returns 500, so Stripe retries real failures.
- `emailOwner` failure log: keeps the existing prefix (`owner email for agent <id> failed`, which ADR-015 and `pnpm owner-link` rely on) and adds the error name, the HTTP status when the error has one, and the message. Emails and URLs in the message are replaced with `<redacted>`, and the message is cut to 200 characters.

## Decisions & alternatives rejected
- Match on the constraint name, not on a new error code: the engine has no agent-not-found error, and the FK is the only ledger write that can name a missing agent.
- Acknowledge with 200 instead of a 4xx: Stripe retries any non-2xx for days, and a retry cannot succeed while the agent is absent from this database.
- No refund and no change to Stripe objects in this task. The unknown-agent top-up needs a human decision (refund in test mode, or find the agent).

## Verification
- `packages/payments/src/index.test.ts`: the unknown-agent case returns 200, logs the exact line with prefixes `be11446e` and `cs_test_a1Fb`, and calls the service once. The other ledger failure (`ledger_stripe_ref`) still returns 500.
- `pnpm verify:fast` green (see the completion report).
