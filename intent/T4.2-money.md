## Why
Money must never be silently stuck. A failed transfer told the worker "it will be retried", but nothing retried it unless Stripe sent another `account.updated`. `needs_review` and `disputed` held the agent's escrow with no way to refund the agent or pay the worker, while the MCP instructions promise that a human review does one or the other.

## What
- `retryPayouts()`, run by `apps/mcp/src/main.ts` every 30 s next to `expireOverdue`: pays up to 25 `verified` tasks whose worker has a Stripe account, oldest first, through the existing `payOut` (key `payout:<task_id>`, unique payout row, paid text only from the call that moves the task to `paid`). `markWorkerOnboarded` reads the same `eyes_payouts_due` filtered to its account.
- `payoutWorker` retrieves the connected account first and throws before `transfers.create` unless `capabilities.transfers` is `active`. A worker who opened the payout link but has not finished onboarding therefore never uses up the `payout:<task_id>` key.
- `resolveTask(task_id, refund|release, note)`: operator-only. Refund returns bounty plus fee to the agent while the escrow is held. Release books release and fee if missing, then pays through the path a verified capture takes. The note is appended to `dispute_reason`.
- Texts to the worker after verification (paid, "your $X is waiting") are skipped for opted-out workers. When one fails, the engine logs only the task id, and the capture, payout or retry batch carries on. The payout is still recorded.
- `007_resolve.sql`: `eyes_payouts_due`, `eyes_resolve_task`, EXECUTE revoked. `scripts/resolve-task.ts` and `pnpm resolve-task` exit 1 before touching the database unless payments and messaging are both live, or `EYES_PROVIDERS=fake` is set.
- Tests for the `bounty_exceeds_max` and `task_type_not_allowed` branches: exact boundary, error context and fix, nothing charged.

## Runbook: resolve a held task
1. Find it: `select id, status, dispute_reason from tasks where status in ('needs_review', 'disputed')`. Look at the photo and the answer.
2. Run with the server's env (database, `EYES_*`, `EYES_PROVIDERS=live`, `STRIPE_*`, `INKBOX_*`): `pnpm resolve-task <task_id> refund "<why>"` or `pnpm resolve-task <task_id> release "<why>"`. Without live Stripe and Inkbox it refuses and changes nothing. Use `EYES_PROVIDERS=fake` only against a local test database.
3. It prints `{"task_id","status"}`: `refunded`, `paid`, or `verified`. `verified` means the money is released but no transfer went through yet: either the worker has no payout account (they were texted the setup link) or the transfer failed. `retryPayouts` or onboarding pays it later, and the server log has the reason. A refusal prints the error body; `issues` gives the reason. A refund is refused once the bounty was released (the task was verified before the dispute): only release is possible then.

## Decisions & alternatives rejected
See ADR-012: same idempotency key on every retry (never a fresh key), capability check before the transfer, no refund after release, note in `dispute_reason` (no new column), no agent-facing route. The status check runs under the task row lock, so refund and release racing on one task cannot both move money; `ledger_once_per_task` rejects any second refund or release.

## Assumptions
- Stripe replays a saved error for the same idempotency key for at least 24 hours, and saves nothing when it never started the request (Stripe idempotency docs, fetched 2026-10-17). Stripe does not retry failed transfers (docs/vendor/stripe.md).
- `stripe.accounts.retrieve(id)` returns `capabilities.transfers` as `active | inactive | pending` (stripe 23.0.0 `esm/resources/Accounts.d.ts`). It is a GET, so it uses no idempotency key. This is the same readiness field the `account.updated` webhook already checks.
- 007 is applied after 006 on InsForge (`scripts/insforge-migrate.ts` applies files in order; live already has 001-006).

## Verification
- Engine int tests on Postgres with fakes, rebased on main (001-007):
  - A payout that fails at capture is paid by the next `retryPayouts`, once, with key `payout:<id>`.
  - `retryPayouts` and the onboarding webhook, both inside the transfer at once (gated fake), pay once.
  - A failed paid text does not stop the rest of a retry batch.
  - A worker who texted STOP is paid (or left `verified`) with no paid or setup text.
  - Paid and setup texts that throw do not fail the capture or the payout, and the log holds the task id but not the phone.
  - Refund and release of held tasks; refund racing release under a held row lock (exactly one wins); wrong-status and refund-after-release refusals.
  - `retryPayouts` skips a worker with no Stripe account.
- Payments unit tests (Stripe HTTP stubbed): GET `/v1/accounts/acct_1` comes before the keyed Transfer. `inactive`, `pending`, missing and absent capabilities throw with no Transfer request sent.
- Script unit test (spawns the script): with no providers set, or with only Stripe or only Inkbox live, it exits 1 with nothing on stdout. With `EYES_PROVIDERS=fake` it gets past the guard.
- Reverted to origin/main's engine, service and migrations: all 7 round-1 adversarial tests fail. Mutants killed:
  - Round 1: no status check, no refund-after-release guard, `paid` never set on release, no row lock, payouts due without an account, `retryPayouts` no-op, release without settle, fresh idempotency key, no max-bounty check, no task-type check.
  - Round 2: no capability guard, only `inactive` refused, no script guard, script guard checking payments only, texts ignoring opt-out, uncaught text failure, text failure logging the error object.
- `pnpm verify:fast` pass. `DATABASE_URL=.../eyes_t42 pnpm test:integration` pass on a fresh database. CI: see PR #45 checks. live-verified: no.

## Known gaps
- A transfer Stripe rejected for another reason (such as an insufficient platform balance) replays the same error for 24 hours under the reused key. The fix is a transfer lookup by `transfer_group` in `packages/payments`, then a fresh key.
- Tasks on accounts that never finish onboarding stay in the oldest-first batch of 25 (one account GET each per run). If 25 or more pile up, they delay newer payouts.
- A dispute after automatic verification can only be released; the worker gets no text when a review is refunded. The capture page still says a setup link was texted to a worker who texted STOP.
