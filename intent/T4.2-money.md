## Why
Money must never be silently stuck. A failed transfer told the worker "it will be retried", but nothing retried it unless Stripe sent another `account.updated`. `needs_review` and `disputed` held the agent's escrow with no way to refund the agent or pay the worker, while the MCP instructions promise that a human review does one or the other.

## What
- `retryPayouts()`: pays up to 25 `verified` tasks whose worker has a Stripe account, oldest first, through the existing `payOut` (key `payout:<task_id>`, unique payout row, paid text only from the call that moves the task to `paid`).
- `resolveTask(task_id, refund|release, note)`: operator-only. Refund returns bounty plus fee to the agent while the escrow is held. Release books release and fee if missing, then pays through the same path a verified capture takes. The note is appended to `dispute_reason`.
- `settle()` in the engine: one "pay now, or text the payout setup link" path shared by `submitCapture` and `resolveTask`.
- `007_resolve.sql`: `eyes_payouts_due`, `eyes_resolve_task`, EXECUTE revoked. `scripts/resolve-task.ts` and `pnpm resolve-task`.
- Tests for the `bounty_exceeds_max` and `task_type_not_allowed` branches: exact boundary, error context and fix, nothing charged.

## Runbook: resolve a held task
1. Find it: `select id, status, dispute_reason from tasks where status in ('needs_review', 'disputed')`. Look at the photo and the answer.
2. Run with the server's env (database, `EYES_*`, `EYES_PROVIDERS=live`, `STRIPE_*`, `INKBOX_*`): `pnpm resolve-task <task_id> refund "<why>"` or `pnpm resolve-task <task_id> release "<why>"`. Check that the first line says `payments: live` before a real release.
3. It prints `{"task_id","status"}`: `refunded`, `paid`, or `verified` (worker texted the payout setup link; `retryPayouts` or onboarding pays later). A refusal prints the error body; `issues` gives the reason. A refund is refused once the bounty was released (the task was verified before the dispute): only release is possible then.

## Decisions & alternatives rejected
See ADR-012: same idempotency key on every retry (never a fresh key), no refund after release, note in `dispute_reason` (no new column), no agent-facing route. The status check runs under the task row lock, so refund and release racing on one task cannot both move money; `ledger_once_per_task` rejects any second refund or release.

## Assumptions
- Stripe replays a saved error for the same idempotency key for at least 24 hours, and saves nothing when it never started the request (Stripe idempotency docs, fetched 2026-10-17). Stripe does not retry failed transfers (docs/vendor/stripe.md).

## Verification
- Engine int tests, all on Postgres with fakes: a payout that fails at capture is paid by the next `retryPayouts`, once, with key `payout:<id>`; `retryPayouts` and the onboarding webhook both inside the transfer at once (gated fake) pay once, one payout row, one paid text; refund of a `needs_review` task returns $3.50, escrow 0, no transfer; release of a disputed `needs_review` task pays, escrow 0, keeps the note; refund racing release under a held row lock: exactly one wins; unknown task, `verified` and `paid` tasks refused; refund after release refused and release then pays the unpaid one and does not pay the already-paid one again; `retryPayouts` leaves a worker with no Stripe account unpaid. The file's `afterEach` ledger invariants check every new task.
- Reverted to origin/main's engine, service and migrations: all 7 new or changed adversarial tests fail. Mutants killed: no status check, no refund-after-release guard, `paid` never set on release, no row lock, payouts due without an account, `retryPayouts` no-op, release without settle, a fresh idempotency key, no max-bounty check, no task-type check.
- `pnpm verify:fast` pass. `DATABASE_URL=.../eyes_t42 pnpm test:integration` 54/54 pass on a fresh database. `pnpm resolve-task` run against that database: usage error exits 1; release of a `needs_review` task prints `paid` and books escrow, fee, payout and release; a second resolve exits 1 with the `invalid_input` body; refund prints `refunded`.
- live-verified: no.

## Known gaps
- `apps/mcp/src/main.ts` does not call `retryPayouts` yet; the one-line change is with the orchestrator.
- A transfer Stripe rejected (such as an insufficient platform balance) replays the same error for 24 hours under the reused key. The fix is a transfer lookup by `transfer_group` in `packages/payments` before creating a transfer, then a fresh key.
- 25 or more tasks stuck on accounts that never finish onboarding delay newer payouts (oldest first); fixing that needs stored onboarding state, which is a schema change.
- A dispute after automatic verification can only be released; the worker gets no text when a review is refunded.
