## Why
Fresh-eyes audit finding 16 (PM journeys): a worker who replied YES and then NO kept the claim. The task stayed `claimed` until its deadline, the agent's `await_answer` waited for nobody, no other worker could take it, and the agent could not cancel it. The capture page told the worker to just close the page, which does exactly that.
## What
- `010_release_claim.sql` adds `eyes_release_claim(worker, now)`. One `update` puts the worker's task back to `dispatched` and clears `claimed_by`/`claimed_at`, only while it is still `claimed` by that worker, before its deadline, with no submission row. It returns the released task, or nothing. EXECUTE is revoked from PUBLIC, anon and authenticated, as in 002 and 004 to 008.
- `handleWorkerReply` NO calls it. If a task came back, the worker gets "Got it, the task is released. Thanks." (38 chars). Otherwise (no claim, past the deadline, photo already sent) the reply is unchanged: "No problem, we will text you the next task nearby."
- Capture page: "Can't make it? Reply NO to the Eyes text to give the task back, so someone nearby can take it."
## Decisions & alternatives rejected
- No new texts to the other offered workers. Their offer rows stay, and `eyes_claim` claims the newest offer whose task is `dispatched`, so their next YES claims it. Texting the offer again would spend Inkbox sends (100 recipients per rolling 24 h per number) and send a second offer for a task most of them already ignored. Rejected for the smallest change; see Known gaps.
- One `update` rather than `select ... for update` and then checks. The update takes the task row lock. Under READ COMMITTED a blocked update rechecks its WHERE against the committed row, so `status = 'claimed'` stops it after `eyes_submit` (which locks the same row and moves the status to `verified` or `needs_review` in the same transaction). If the release wins, `eyes_submit` then reads `claimed_by` null and raises `task_already_claimed`. A concurrent YES from another worker goes through the same row: `eyes_claim` updates only `where status = 'dispatched'`, so it either finds the task still claimed (the worker gets "already claimed" and can reply YES again) or claims the released task. Never two claims.
- The no-submission check is kept because the card asks for it, but `status = 'claimed'` already implies no submission today (only `eyes_submit` inserts submissions). On its own it is not race-safe: the update's recheck reads `submissions` with the statement's snapshot. Removing only the status check makes the race test release a verified task (checked, see Verification).
- No agent-facing change. After a release `get_task` shows `dispatched` with `claimed_at: null`. `await_answer` keeps polling with the `dispatched` next_step ("No worker has claimed the task yet..."). `cancel_task` works again, because it refunds any `dispatched` task. A NO after the deadline does nothing; expiry refunds the task.
## Assumptions
- The text goes to a worker who has already texted us, so the Inkbox cold-contact limits (159 chars, no links) do not apply; the reply is within them anyway (docs/vendor/inkbox.md, Limits).
- InsForge RPC returns a `setof tasks` function's rows as a JSON array, as for `eyes_cancel_task`.
## Verification
- `packages/engine/src/engine.int.test.ts` "a NO after YES gives the task back...": A and B are offered; A claims, B's YES loses. B's NO (no claim) gets the old text and the task stays `claimed`. A's NO gets the release text (at most 159 chars); `get_task` is `dispatched` with `claimed_at` null; `await_answer` returns `dispatched`, not answered. B's YES then gets the capture link, A's old capture link is refused with `task_already_claimed`, and B's photo verifies. A NO from B after the photo gets the old text, and the task stays `verified` with the answer.
- `packages/db/src/dispatch.int.test.ts` "a NO gives the claim back only before the deadline...": 20 reps. Each rep first checks that a NO at the deadline releases nothing. Then a transaction holds the task row lock, and the release and `eyes_submit` start on separate pooled connections, in alternating order. The test waits until both show as Lock waiters in `pg_stat_activity`, then commits. Every rep ends with exactly one outcome. NO first: released, submit raised `task_already_claimed`, 0 submissions, `dispatched`, `claimed_by` null. Photo first: nothing released, 1 submission, `verified`, still claimed by the worker. 3 runs, all pass.
- Fail on the old code: with `index.ts` from origin/main and no 010, on a fresh database, both tests fail. The engine test gets "No problem..." instead of the release text. The DB test fails because `eyes_release_claim` does not exist. Mutation: 010 without `t.status = 'claimed'` fails the race test (`released: 1`, task `dispatched` after a verified submit).
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t414 pnpm test:integration`: 6 files, 81 tests pass on a fresh database, and again on the same one.
- On `eyes_t414` a fresh role has no EXECUTE on `eyes_release_claim(uuid,timestamptz)`; `proacl` is `{postgres=X/postgres}`.
- `pnpm verify:fast`: pass.
- Capture page before and after at 390 and 1280: `pr-assets/eyes/T4.14/capture-{before,after}-{390,1280}.png`.
- Live-verified: no (texting is simulated on the deployed server).
