## Why

An incorrect classifier refusal needs a review ticket rather than repeated paid attempts or a weaker global safety setting. Manual approval must apply only to the exact request that was reviewed.

## Behavior

A decoded classifier `unsafe_task` rejection offers Report incorrect block. Network errors, spending errors and explicit rules-layer blocks do not. The widget preserves the exact refused Ask, including the typed question, location, task type, bounty and original Ask idempotency key. Reporting uses a separate stable per-card key and sends the decoded error as untrusted context to `report_classifier` with `ask_idempotency_key` naming the original request key.

The ticket is displayed without changing the question field. Check review status calls `get_classifier_report`; neither reporting nor checking charges or dispatches. Rejected and expired reports are explained. Approval enables only an explicit Retry original request with the original Ask plus `classifier_report_id`; editing the question disables that retry until the original is restored. Normal backend spend checks and exact-request approval checks remain authoritative. A consumed approval offers only View existing task, never another Ask.

The backend tools, authenticated storage, operator decisions, expiry and one-use grant are owned by T6.63. This widget must be released with those tools, not before them. Existing MCP Apps/OpenAI bridges are preserved. Report tool host notifications do not erase the original card. Nested host `detail`/`TextContent` errors are decoded using bounded JSON parsing, never evaluation.

## Verification

Real click tests run both MCP Apps and OpenAI bridges: report payload, busy controls, duplicate-safe retries, pending/status/approval, edited-question prevention, exact original retry, rejected/expired/consumed outcomes, report failure, and ineligible errors. Tests assert the Ask tool is not called again before explicit approved retry. Source-text snapshots are not used for these behaviors.
