## Why
Manufact's publishing audit (end-to-end plus policy review) of the keyless sandbox (https://bold-pulse-f6t7q.run.mcp-use.com/mcp, audit 7cf0b542, 2026-10-17 13:4x PT) came back "ready for Claude, NOT ready for ChatGPT", with these findings:
1. ERROR `view-domain-present`: "1 ChatGPT UI domain issue(s) found", "ui://views/task-card.html: missing domain". Hint: "For ChatGPT submission, set one exact HTTPS origin such as "https://app.example.com" on every view via _meta.ui.domain (or openai/widgetDomain)."
2. WARNING `tool-invocation-metadata-present`: `show_task` is missing `openai/toolInvocation`. Hint: "add openai/toolInvocation with string fields invoking and invoked".
3. WARNING `tool-resource-metadata-complete`: "ui://views/task-card.html incomplete metadata". Hint: "Use a ui:// URI and text/html;profile=mcp-app. For mcp-use v1, use widgetMetadata.metadata.widgetDescription; for v2, use the bound tool's view.description."
4. POLICY: "ask_eyes is marked destructiveHint: false, while its description says it escrows a bounty and fee and later pays a worker after verification." The policy: "Use `false` only for additive writes without destructive or irreversible effects."
5. POLICY: "The quote_task and ask_eyes schemas accept a free-form address and latitude/longitude directly from the model", against "Do not request precise user location data".

## What
- `ask_eyes` declares `destructiveHint: true` (finding 4): it spends the caller's money and can end in a payout that cannot be undone. `idempotentHint` stays `true`, because the same `idempotency_key` returns the original task.
- `location` says it is the public place to check (finding 5). The text lives in the frozen `LocationInput` schema, so ADR-024 records the description-only change; the contract snapshot, `openapi.json` and `llms-full.txt` are regenerated. The `quote_task` and `ask_eyes` tool descriptions say the same in one clause each.
- `show_task`, when the card is built, advertises progress labels for ChatGPT (finding 2): `"openai/toolInvocation": { invoking: "Loading the Eyes task card", invoked: "Eyes task card ready" }`, plus the same two strings under `openai/toolInvocation/invoking` and `openai/toolInvocation/invoked`. Set through the tool definition's `_meta`, which mcp-use passes through next to the `ui` keys it derives from `view`.
- Tests: the tools/list test requires `destructiveHint: true` on `ask_eyes`; the card binding test requires both forms of the labels on `show_task`.
- Findings 1 and 3 are not changed in code; see Decisions.

## Decisions & alternatives rejected
- Finding 1 is not fixed with `view.domain`, the SDK option for `_meta.ui.domain`, because it would break the card in Claude. mcp-use 2.10 sends the authored domain verbatim to every client except Claude, and to Claude sends the first 32 hex characters of the SHA-256 of the authored string plus `.claudemcpcontent.com` (`applyClaudeResourceDomain`, which picks Claude by client name or user agent). Claude accepts `ui.domain` only when it is exactly that hash of the full connector URL, path included, and otherwise shows "Invalid ui.domain format" or "ui.domain mismatch" instead of the app (claude.com/docs/connectors/building/mcp-apps/troubleshooting). ChatGPT and this audit want the bare origin, and our connector URL ends in `/mcp`, so no single authored string works for both. Probed locally with `view.domain` set to `https://bold-pulse-f6t7q.run.mcp-use.com`: a client named `claude-ai` on our stateless server received the raw origin (no per-request client info, so no rewrite), and a Claude client that is recognised would get `68526630ba9fe32e11eade2ae21fa89f.claudemcpcontent.com`, while Claude expects `f86cc13ab29c43d93c70cf4b638320c0.claudemcpcontent.com` for `https://bold-pulse-f6t7q.run.mcp-use.com/mcp`. Today, with no domain, Claude renders the card in its default sandbox, which is why the audit calls it ready for Claude.
- `openai/widgetDomain` (the hint's alternative, ignored by Claude) cannot be set on the card either. OpenAI documents it, and `openai/widgetDescription`, as resource contents `_meta` keys (`resources/read`), but mcp-use 2.10 builds the view resource's contents `_meta` only from `view.csp`, `permissions`, `domain`, `prefersBorder` and the view's display modes, and its `mcp:resources/read` middleware wraps only resources registered with `server.resource`, not view resources (`#registerViewResource` calls the SDK's `registerResource` directly). Tried: a `mcp:resources/read` middleware adding both keys never ran for `ui://views/task-card.html`.
- Finding 3: `show_task` already sets `view.description`, the v2 option the hint names, and it appears on `resources/list`. mcp-use 2.10 does not copy it to the `resources/read` contents (its own type docs say it does), and the MCP contents schema strips a `description` field, so there is no SDK option left to set. The likely gap is `openai/widgetDescription` in the read contents, which is blocked as above.
- Both progress label forms for finding 2: the audit asks for an `openai/toolInvocation` object, while OpenAI's Apps SDK reference lists the flat `openai/toolInvocation/invoking` and `openai/toolInvocation/invoked` keys (64 characters at most) that ChatGPT reads.
- The labels and the tool `_meta` exist only when the card is built, so `show_task` without a views manifest, and every other tool, still list no `_meta`.
- Tool description wording stays short: in sandbox mode the `quote_task` and `ask_eyes` descriptions and the server instructions are prefixed with the 584-byte sandbox notice (after #88). `ask_eyes` is 1,460 bytes, 2,044 in sandbox mode; `quote_task` 1,424, 2,008 in sandbox mode. Both under 2 KB, with 4 bytes to spare on `ask_eyes`, so the next sentence added to the notice or to `ask_eyes` needs a cut elsewhere.

## Assumptions
- Manufact's audit reads the same `tools/list` keys as the test asserts, so finding 2 clears after the sandbox redeploys.
- Findings 1 and 3 need either an mcp-use change (a domain for ChatGPT separate from the one hashed for Claude, or hashing the connector URL; and passing `view.description` and extra keys into the read contents) or an owner decision to give up the Claude card on this server. Not decided here.
