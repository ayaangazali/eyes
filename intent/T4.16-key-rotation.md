## Why
#28: a leaked `api_key` could only be killed by rotating `EYES_LINK_SECRET`, which breaks every link and capability email address for every agent. The owner console (ADR-011) is the per-agent surface the agent never sees, so the owner now replaces one agent's key there and nothing else changes. Capability links stay as they are (ADR-019).

## What
- Contract (ADR-019): `EyesService.rotateApiKey(token): Promise<{ api_key }>` and `HTTP_ROUTES.owner_rotate_key = "POST /owner/:token/rotate-key"`. `cli/src/docs.ts` already excludes `owner_*` routes from agent docs, so it is unchanged.
- `011_rotate_key.sql`: `eyes_rotate_api_key(agent_id, api_key_hash)` overwrites `agents.api_key_hash` for one agent and returns its id; EXECUTE revoked from public, anon and authenticated.
- Engine: `rotateApiKey` checks the `p:` token like `ownerConsole`, makes the key with the same `newApiKey()` that `signupAgent` now uses (prefix by `test_mode`, 32 random bytes, SHA-256 stored), returns it once, and throws `owner_link_invalid` for an unknown agent.
- Payments: the console ends with "Replace this agent's API key", a warning and a POST form. `POST /owner/:token/rotate-key` renders the new key once (escaped, `word-break` so it fits a phone) with a link back; `/owner/*` headers (no-store, no-referrer, CSP) apply; a bad link gets the existing 404 page.

## Decisions & alternatives rejected
- `newApiKey()` is extracted from `signupAgent` so both paths make keys the same way; signup behaviour is unchanged.
- The result is a 200 page from the POST, not a 303 to a GET, so the key is never in a URL, history entry or log line (`apps/mcp` logs the route as `/owner/<token>/rotate-key`).
- No confirmation step beyond the warning: the action is recoverable (replace again) and the owner link is the authorization.
- Rejected: a generation counter on `agents` (new column, and it also revokes links, which is out of scope); letting the agent rotate its own key (the leaked key's holder could lock the agent out).

## Assumptions
- `011` does not depend on `010` (open PR #61); the runner applies files by name, so either order works on an existing database.

## Verification
- `pnpm verify:fast`: pass.
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t416 pnpm test:integration`: pass, on a fresh database migrated through 011.
- Engine int: after `rotateApiKey` the old key authenticates as null at once, the new one authenticates as the same agent and `getBalance` works; the new key is in no email, text, console call, owner console, `get_balance`, `get_spend_policy` or `agents` row; `t:`/`o:`/`c:`/wrong-secret/3-part/garbage/unknown-agent tokens reject with `owner_link_invalid` (404) and the old key keeps working; two concurrent rotations leave exactly one of the three keys valid.
- Route unit: console has the form and warning; POST answers 200 with the key escaped, private headers and no `location`; GET on the rotate path is 404 and never calls the service; a bad link is 404; the key is in no other response.
- Ran against `origin/main` source with the new tests: all 4 fail (`rotateApiKey is not a function`, missing route). Mutants killed: key logged with `console.info`, key rendered with `raw()`.

- Verifier: security+spec+test+intent **PASS** ([verdicts/T4.16-PR63.md](verdicts/T4.16-PR63.md)): only a valid p: token rotates; the old key fails immediately on REST and MCP (stateless transport checks the key per request); the new key appears once and in 0 of 108 log greps; 20x5 concurrent rotations leave exactly one valid key.

## Known gaps
- Owner links and capability email addresses still have no per-agent revocation (rest of #28).
- No 390 px render check was run (no local browser runs on this machine); `.key` uses `word-break: break-all` so the 53-character key wraps.
