## Why
Gate G3 is "the demo script (§13) passes 3 times in a row". `e2e/demo.spec.ts` turns that script into a machine check on fake providers, so a broken demo step fails CI instead of failing on stage. `scripts/swarm.ts` is the local half of the swarm demo mode: about a minute of simulated agents and workers around San Francisco so the dashboard map lights up and the ledger fills, without live keys.

## What
- `e2e/demo.spec.ts`, one rehearsal per §13 step on the real MCP server, engine, Postgres, Inkbox and Primitive webhook routes, worker capture page and dashboard server: MCP `quote_task` then `ask_eyes` for Blue Bottle, Mint Plaza (3 workers, $3.50 escrowed); the dashboard `/feed` has the task at the cafe's coordinates with `workers_notified: 3` and the rendered page's headline reads "3 workers notified near ..."; a signed `imessage.received` YES gets the capture link; the capture page (fake camera, GPS at the cafe) shows "Verified and paid"; `await_answer` returns `paid`, all checks true, distance under 150 m, cost 3.5; the agent's $20 signup top-up is exactly one `topup` ledger row (2000 cents, no task; the run's database holds only this agent); exactly one 300-cent fake transfer and exactly one escrow 350, release 300, fee 50, payout 300 ledger row for the task; the dashboard headline turns to "worker paid $3.00" and its ledger shows "Released for the worker $3.00" (§13 step 4). Second test: "Photograph the house at 123 Oak St" must be `unsafe_task`, category `private_residence`, with a `fix`. Without `DATABASE_URL` the spec skips locally but fails in `beforeAll` when `CI` is set, so the G3 check cannot read green by skipping. Third test: a signed Primitive `email.received` to the agent's Eyes address gets a threaded "Got it" reply, then (after a YES and a capture) a reply with `in_reply_to`/`references` set and the photo attached.
- `scripts/swarm.ts` (`pnpm swarm --agents 50 --tasks 2`): in-process engine on `DATABASE_URL` with fake providers; 40 workers (seeded PRNG, round-robin around 15 public SF places, opted in with fake payout accounts); N agents signed up ($20 test grant); N x tasks tasks at those places with matching task types and $2 to $5 bounties; fates 50% paid, 20% claimed, 15% cancelled, 15% expired, posted over 45 s, acted on 1 to 5 s later, paid ones captured 3 to 8 s after the claim; prints each event and a summary read through `eyes_dashboard_feed`. Refuses `EYES_PROVIDERS=live` always, a missing `DATABASE_URL`, and a non-localhost `DATABASE_URL` unless `--allow-remote`.
- `package.json`: `test:demo` (`playwright test e2e/demo.spec.ts --repeat-each=3 --workers=1`) and `swarm`; root devDependency `postgres@3.4.9` (the version `packages/db` uses; approved by the orchestrator) so the spec can `CREATE DATABASE`.

## Decisions & alternatives rejected
- Own database and ports per run: CI runs the e2e files on 2 workers, so `golden-path.spec.ts` and this spec start together. Golden assumes it is the only spec with workers at the cafe and binds 3399. The spec creates `eyes_demo_<hex>` on the `DATABASE_URL` server, migrates it, drops it in `afterAll`, and listens on ephemeral ports. The prebuilt capture page has `http://127.0.0.1:3399` baked in, so `page.route` forwards those requests to this run's API. Verified by running the whole suite with `--workers=2`: golden and demo ran side by side and both passed.
- `CREATE DATABASE` needs a raw client and files under `e2e/` resolve packages from the root only, so `postgres@3.4.9` is a root devDependency. The first version loaded it through `createRequire` anchored at `packages/db`; the orchestrator approved the dependency and the workaround was deleted.
- Dashboard step: Leaflet and tiles come from third-party CDNs, so the spec aborts `unpkg.com` and asserts the pin through `/feed` (status, lat, lng, `workers_notified`) plus the page's headline, which renders without the map.
- Refusal: T1.5 (#7) merged while this was in review, so the spec uses `createAssessTask({})` (the real rule layer; `{}` keeps the classifier off without a key, as in CI) and the refusal test runs unconditionally. The first version carried a stub probe and a `test.fixme`; both were deleted on rebase.
- iMessage, not SMS: the live demo uses the Inkbox iMessage line (#24), so the YES/START webhooks send `imessage.received`.
- Email test capture posts multipart straight to `/w/offers/:token/capture`; the page itself is covered by the first test.
- Swarm expiry: `deadline_minutes` is at least 5, so expiring tasks are posted with the clock set back so the deadline lands 0 to 4 s after posting, and `expireOverdue` runs 1 s after that. Setting the clock forward instead would date the refund rows minutes into the future and keep them above a real demo's rows in the dashboard ledger.
- Swarm claims follow T4.6 (migration 006): dispatch skips busy workers (holding a claimed task) and a busy worker's YES returns their own task; otherwise YES claims the worker's newest open offer. The swarm tracks both, picks an idle notified worker whose newest open offer is this task, and retries every 2 s until 52 s. After merging 006, the first timings (claims 3 to 12 s, captures 4 to 12 s after posting) left 25 of 77 claims with all three notified workers busy; claiming 1 to 5 s after posting and capturing 3 to 8 s later claims all 77.
- Swarm safety is the real rule layer, `createAssessTask({})`: every templated question passes it, and passing `{}` keeps a locally set `ANTHROPIC_API_KEY` from sending 100 live classifier calls.

## Known gaps
- The dashboard reads the newest 50 tasks and the newest 50 ledger rows. After a 100-task swarm that window holds only paid, claimed and cancelled tasks and mostly payout, release, fee and escrow rows (measured above: 2 refunds, no topups). Expired tasks are posted with backdated clocks, so they are always older than the window; the topups come before every task. The full mix shows only through `eyes_dashboard_feed` with a larger limit, as in the swarm's summary.
- Swarm workers stay opted in near the demo places. Never point the swarm at the database a live demo dispatches from: they would take the nearest-3 slots. The guard blocks non-local databases unless `--allow-remote`.
- The Blaxel batch-job wrapper (T3.5, remote half) is not built.
