## Why
Every Checkout payer got the `p:` owner link, and the `t:` top-up link is agent-visible, so anyone who got hold of it and paid the minimum became an owner of a balance someone else funded (#54). A replayed webhook also sent the link again. The public signup relayed an agent-chosen name of up to 80 characters to any address.

## What
- `014_first_paid_topup.sql`: `eyes_credit_paid_topup` locks the agent row, checks for an earlier paid top-up (any `topup` row except the `signup:<agent id>` grant), credits through `eyes_credit_topup`, and returns `first_paid` only if this call wrote the first paid row.
- `creditTopup` emails the payer only when `first_paid`; second payers, replays and concurrent redeliveries send nothing.
- Signup and payer emails name the agent by id ("An AI agent (Eyes agent id ...)"), never by its chosen name.
- Signup email, payer receipt and owner console say "The first person who pays for this agent also gets this link."
- ADR-015 addendum.

## Decisions & alternatives rejected
- One locking function instead of a read RPC before the credit: separate RPCs are separate transactions, so two first payments at once could both see "none yet".
- Exclude the signup grant by its exact ref, not by "has a Stripe ref": `eyes_signup` records the grant with `stripe_ref = 'signup:<id>'`.
- Payer receipt drops the agent name too: the engine no longer loads the agent row for it, and no owner email then carries agent-chosen text.
- Masked owner email on the top-up page not built: the signup `owner_email` is not stored and the task excludes new columns (see Known gaps).

## Assumptions
- Real Stripe refs are Checkout Session ids, unique per session and tied to one agent through `metadata.agent_id`.
