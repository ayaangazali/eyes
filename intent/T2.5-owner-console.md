## Why
`get_spend_policy` tells agents "only your user can change these limits", but no user surface existed, and the Stripe track asks for clear user control over what agents can do and spend. The top-up link cannot be that surface because the agent holds it, so the owner gets a separate `p:` capability link the agent never sees (ADR-011).

## What
- `005_owner.sql`: `eyes_owner_console` (balance, escrow, spent today in UTC and policy via `eyes_agent_summary`, last 20 tasks, last 50 agent ledger rows as jsonb) and `eyes_update_spend_policy` (sets `max_bounty_cents`, `daily_cap_cents`, `allowed_task_types`, returns the new summary). No tables or columns. EXECUTE revoked from public, anon, authenticated.
- Engine: `ownerConsole(token)` and `updateSpendPolicy(token, input)` accept only verified `p:` tokens, else `owner_link_invalid`; cents internally, USD at the edge. `signupAgent` emails `owner_email` the owner link through `providers.email` and says so in `next_step`; the link is in no tool output, error or log line. `getSpendPolicy` shares the `policyOf` mapping.
- Payments routes: `GET /owner/:token` server-rendered page (no JS, 390 px wide, labelled 16 px inputs, add-funds button to the agent's `/topup/:token`, tasks and ledger); `POST /owner/:token/policy` form post validated with `OwnerPolicyInput`, 303 back with a saved notice, 400 re-render on bad input, 404 page on a bad link. `Referrer-Policy: no-referrer`, `Cache-Control: no-store` and a CSP on every `/owner/*` response.
- `scripts/owner-link.ts` (`pnpm owner-link <agent_id>`) prints the owner URL from `EYES_LINK_SECRET` and `EYES_PUBLIC_API_URL`.

## Decisions & alternatives rejected
- Mounted inside `stripeRoutes`, so `apps/mcp/src/server.ts` is unchanged; `/owner/*` is outside the bearer-auth paths.
- Owner email failure (Primitive allowlist, ADR-004) does not fail signup: the agent and its API key already exist, so signup returns and `next_step` says the operator can send the link. The log line carries only the agent id and error name, because an adapter error could echo the body.
- Max bounty and allowed types are read from the agent row on each request (auth is per request), the daily cap inside `eyes_post_task` under the row lock, so a change applies to the next call with no cache to invalidate.
- Empty form numbers become NaN, not 0, so a blank field cannot silently freeze spending. No checkbox checked means no task types allowed.
- Ledger shows rows carrying the agent id (top-up, escrow, release, fee, refund); worker payouts are platform-to-worker and stay off the owner page.
- Rejected: reusing the `t:` token (agent holds it); owner accounts with login (ADR-011).

## Assumptions
- `Email.send` adapters choose the sender address; the owner email is plain text.
- The page is served at the root of the public API host, so the form posts to `/owner/<token>/policy`.

## Known gaps
- Signup is public, so anyone can make Eyes send one owner email to an address they choose (agent name is JSON-quoted on one line). Needs signup rate limiting.
- A leaked owner link grants control until `EYES_LINK_SECRET` rotates; no per-link revocation (ADR-011).
- `next_step` says the owner was emailed whenever `Email.send` resolves, including with fake email when `PRIMITIVE_API_KEY` is unset.
- No per-agent index on `ledger.agent_id`; the console scans the ledger, fine at event scale.
