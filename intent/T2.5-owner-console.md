## Why
`get_spend_policy` tells agents "only your user can change these limits", but no user surface existed, and the Stripe track asks for clear user control over what agents can do and spend. The top-up link cannot be that surface because the agent holds it, so the owner gets a separate `p:` link the agent never sees (ADR-011).

## What
- Engine: `ownerConsole` / `updateSpendPolicy` accept only verified `p:` tokens, else `owner_link_invalid`; cents inside, USD at the edge, task types deduped. `signupAgent` emails `owner_email` the link and says so in `next_step`; the link is in no tool output, error or log line.
- Payments: `GET /owner/:token` server-rendered page (no JS, 390 px, labelled 16 px inputs, add funds via `/topup/:token`, refund-path line, "Frozen" at cap 0, tasks, ledger); `POST /owner/:token/policy` validated with `OwnerPolicyInput`, 303 with a saved notice, 400 re-render, 404 on a bad link; no-referrer, no-store and CSP on every `/owner/*` response. `pnpm owner-link <agent_id>` prints the URL.

## Decisions & alternatives rejected
- `005_owner.sql` adds two RPC functions (read `eyes_owner_console`, update `eyes_update_spend_policy`) with EXECUTE revoked, and no tables or columns, so the data model is unchanged as ADR-011 intends.
- Mounted in `stripeRoutes`, so `apps/mcp` is unchanged and `/owner/*` sits outside bearer auth. Limits apply on the next call: auth reads the agent row per request and the cap is checked under the row lock in `eyes_post_task`.
- A failed owner email does not fail signup (the agent and key already exist); `next_step` points to the operator and the log carries only agent id and error name.
- Form amounts must be plain decimals with at most 2 places; blank, `0x10`, `1.005` re-render 400 instead of rounding or reading as 0. Ledger lists rows carrying the agent id; worker payouts stay off the page.
- Rejected: reusing the `t:` token (agent holds it); owner logins (ADR-011).

## Assumptions
- `Email.send` adapters pick the sender; the page is served at the API host root.

## Verification
- `pnpm verify:fast` pass; `DATABASE_URL=.../eyes_t25owner pnpm test:integration` pass on a database migrated through 005.
- Engine int tests: link only in the email, absent from signup, `get_balance`, `get_spend_policy` and the `insufficient_balance` body; lowered bounty, removed type and cap 0 make `ask_eyes` throw `bounty_exceeds_max`, `task_type_not_allowed`, `daily_cap_exceeded`; console parses `OwnerConsole`; t:/o:/c:/wrong-secret/3-part/unknown-agent tokens rejected; duplicate types saved once; a failing email whose error carries the URL logs no `/owner/`.
- Route tests: `<script>` question, name and place escaped; 303 + notice with multi-value checkboxes; blank, out-of-range, hex and 3-decimal amounts 400 without saving; 404 on a bad link; Referrer-Policy, Cache-Control and CSP on 200/303/400/404.
- Mutants killed: any token kind, ignored bounty, URL in `next_step` or error body, raw question, each owner header, CSP `script-src *`, loose amount parsing, `String(err)` in the log, no dedupe. 390 x 844 Chromium render: no overflow, 16 px inputs, all labelled.
- Round 1 verifiers: security PASS, spec+test+intent PASS; their minors are fixed in round 2. CI on the final head: PR #35 checks. live-verified: no.

## Known gaps
- The agent supplies `owner_email`, so it can route the owner link to an inbox it reads and raise its own limits (follow-up issue filed by the orchestrator).
- Public signup can relay one Eyes email with an 80-char agent-chosen name to any address (JSON-quoted, constant subject); needs signup rate limiting (T4.1) or dropping the name.
- No per-link revocation until `EYES_LINK_SECRET` rotates (ADR-011); `next_step` claims an email was sent with the fake provider too; the 20-task limit and `ledger.agent_id` scan are untested and unindexed, fine at event scale.
