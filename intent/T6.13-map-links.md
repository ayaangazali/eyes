## Why
Workers paste map links into the Eyes thread to say where they are. Those texts went to the "unknown" reply (or a HELP ticket), so the saved spot stayed stale and the worker had to find the HERE link instead.

## What
- `parseMapLink(text)` in `@eyes/core` reads coordinates anywhere in a text: `maps.apple.com/?ll=`, `?q=` with coordinates, `?sll=` (`address=` is ignored), `maps.apple.com/place?coordinate=`, `google.com/maps/@LAT,LNG,zoom`, `google.com/maps?q=LAT,LNG`, `google.com/maps/place/.../@LAT,LNG`, and plain decimal "LAT, LNG" pairs. Same checks as `POST /w/location`: lat within ±90, lng within ±180, not 0,0.
- Short links (`maps.app.goo.gl`, `goo.gl/maps`) carry no coordinates. The parser returns `"short_link"` and never fetches or expands a URL (no SSRF, no third-party lookup of a worker's link).
- Engine: a worker text with intent `unknown` that holds a map link stores the fix through `eyes_store_location` (same rate limits as other fixes) with source `map_link`, and replies "Spot updated: near 37.76, -122.39." (2 decimals). Rate limited: a text to wait. Short link: a HERE link with a note that short links can't be read. Coordinates are never logged.
- Migration 019 widens `workers_location_source_check` to add `map_link` (all 017 values kept). Forward-only.
- An iMessage whose text is only U+FFFC/U+FFFD placeholders counts as an empty location share (HERE link reply); before, only a single U+FFFD did.
- Privacy pages (worker and landing) list texted map links and "lat, lng" pairs as a way the latest spot is replaced.

## Decisions & alternatives rejected
- Detect in the `unknown` branch, no new reply intent: every map-link text already classifies as `unknown` (URLs contain "?" or extra words), so the Inkbox route and `REPLY_INTENTS` stay unchanged.
- `map_link` stays out of the `POST /w/location` source enum: only texts produce it.
- Expanding short links by fetching them: rejected (SSRF, and it would send the worker's link to Google from our server).
- Plain pairs need at least 3 decimals in both numbers (copied coordinates have 4-6), so "12, 34" or a price like "4.50, 3.20" in a ticket text is not a location. Map links keep any precision.

## Verification
- Unit: `packages/core/src/util.test.ts` covers each format, junk, out of range, 0,0, short links. `inkbox.test.ts` covers U+FFFC.
- Integration (local eyes-pg, 019 applied with `pnpm db:migrate`): `location.int.test.ts` stores an Apple link as `map_link`, rate limits a second link, and answers a short link with a HERE link without changing the spot.
- `pnpm verify:fast` green.
