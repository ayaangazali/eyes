## Why
A worker's setup is spread over several texts and pages: the join, the spot, the iPhone app, payouts and earnings each have their own link. The UX review (opportunity #1) asked for one checklist that shows what is done and offers the next step, linked from the texts.

## What changed in this batch
- `GET /w/me` and `POST /w/me/install` (ADR-028). The code is the worker's signed "e:" token (the earnings token) and travels only as `Authorization: Bearer`; the page reads it from `#c=` and clears the fragment. GET returns opt-in, spot age and freshness, whether the last fix came from the app, payout state with the Stripe onboarding link, the HERE and earnings links, and the 5 newest tasks; `Cache-Control: no-store`. Only POST mints a location code for the install link, so viewing the page never rotates out a device's code. Data from the existing `eyes_worker` and `eyes_worker_earnings` RPCs; no migration.
- `payoutOf` is shared by the earnings page and the setup page, so both label payouts the same way.
- START ends with ` Your setup: <worker web>/me#c=<token>`; HELP's link is now the setup page instead of the earnings page (the setup page links to earnings).
- `/me` (worker web): title "You're set up" or "Finish setting up"; four rows (number joined, spot fresh, Eyes app sending, payouts) with one primary action on the first open row; "Your last tasks" with status, amount and payout state, and "All earnings". States: loading skeleton, no code and expired link (Text HELP button), network error (Try again). Motion per the Emil rules: rows fade and rise in 50ms apart with the shared ease-out when data arrives, the install button shows the busy spinner, reduced motion fades without movement.
