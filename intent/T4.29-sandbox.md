## Why
Every Eyes tool needs `Authorization: Bearer <api_key>`, and Manufact Cloud's eval suites, Public Chat and Inspector can only authenticate to a server through OAuth (`/api/v1/servers/{id}/credentials/connect` is OAuth-only). So none of them can call a single Eyes tool today, and a judge has to sign up and manage a key before seeing the flow. The live server cannot just drop the key: `ask_eyes` offers tasks to real opted-in workers from the shared `workers` table, and a real person's YES could claim a task nobody paid for. Agents, judges and Manufact's harness need a server where quote_task, ask_eyes and await_answer return a verified answer with no key, without touching real workers or money.

## What
- `apps/mcp/src/main.ts`: `EYES_SANDBOX=1` builds the service with `createSandboxService`. It refuses to start with `EYES_PROVIDERS=live`, any `EYES_FAKE_WEBHOOKS` or any `ANTHROPIC_API_KEY`, and the error says why.
- `apps/mcp/src/sandbox.ts` (new), using only existing service methods:
  - `createSandboxService` wraps the fake messaging provider the engine is built with, and acts only for sandbox numbers (`+1`, area code, `55501`, two digits: the fictional 555-01XX range). An offer to such a worker is answered YES at once, and 5 seconds after the capture link arrives the worker submits a capture at the task's coordinates with a fresh `captured_at`, an answer text that starts "Simulated sandbox answer, nobody went:" and a 12-byte JPEG header; fake vision passes it, so the task reaches `verified`. A worker with any other number is never answered for. `ask_eyes` joins a worker with a random sandbox number at the resolved location and texts START when its quote shows no free worker; `quote_task` writes nothing and reports `workers_nearby` 1 (`est_minutes_to_answer` 1) in that case, because the ask adds one. `ask_eyes` runs one at a time, so each YES claims the task it was just offered; each ask gets 15 seconds once its turn comes and at most 10 wait, past either it answers `rate_limited`. `ask_eyes` and `await_answer` `next_step` start with the sandbox sentence.
  - `keylessAgents` gives a request with no `Authorization` header an agent keyed on the caller's address (one hour after its last request, at most 10,000 addresses, at most 30 new agents a minute), made by `signupAgent` plus `updateSpendPolicy` (daily cap 1,000 USD), and topped up with 1,000 USD of play money whenever its balance is under 100 USD. When a held key stops authenticating, that request is 401 and the address gets a new agent on its next request.
- `apps/mcp/src/server.ts`: in sandbox mode only, the bearer middleware asks `keylessAgents` when the `Authorization` header is absent; any header still goes through `authenticate`. HOME and `/status` show "Sandbox: keyless, simulated worker, no real people or money." with how to call it, that `quote_task` counts the worker an ask adds, and that only the three demo place names resolve (pass `{lat, lng}` for any other place); they drop the "no task gets answered" texting line and the separate place-lookup line. The MCP instructions and the `quote_task` and `ask_eyes` descriptions start with the same notice; the server description starts with the sandbox sentence.
- `.env.example` lists `EYES_SANDBOX`; `docs/DEPLOY.md` says how the sandbox server is configured and deployed.

## Decisions & alternatives rejected
See [ADR-023](decisions/ADR-023-keyless-sandbox.md). In short:
- An agent per caller address, not per MCP session: mcp-use 2.10 is stateless and issues no session id (checked with a probe: no `mcp-session-id` on any response). Callers behind one address, such as everything coming from Manufact, share one agent, so its daily cap is raised to 1,000 USD and its balance is topped up; the daily cap remains the per-address limit.
- Keyless only in a separate server with its own database, never a flag on the live one.
- YES at dispatch inside a serial `ask_eyes`, not after a delay: a delayed YES claims the worker's newest offer, which can belong to a parallel task. Without the queue, three parallel asks at one place failed with `no_workers_nearby` in 4 of 4 runs.
- Free workers are reused instead of one new worker per task.
- The simulator acts only for 555-01XX numbers, so it never claims or captures for a real worker even if the sandbox is pointed at a database that has them.
- The shared 30-a-minute creation budget can be used up by one caller with many IPv6 /64s; accepted and recorded in the ADR rather than adding a per-/48 count.

## Assumptions
- One sandbox server instance: the ask queue, the keyless map and pending captures are per process.
- Manufact forwards the caller address as the right-most `X-Forwarded-For` entry, as the signup throttle already assumes.
- The sandbox deploy does not set `INKBOX_*`, `STRIPE_*` or `PRIMITIVE_*` (`EYES_PROVIDERS=fake` makes them unused) and has its own InsForge project; the code cannot tell which database it was given.
