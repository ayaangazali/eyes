## Why
Every Eyes tool needs `Authorization: Bearer <api_key>`, and Manufact Cloud's eval suites, Public Chat and Inspector can only authenticate to a server through OAuth (`/api/v1/servers/{id}/credentials/connect` is OAuth-only). So none of them can call a single Eyes tool today, and a judge has to sign up and manage a key before seeing the flow. The live server cannot just drop the key: `ask_eyes` offers tasks to real opted-in workers from the shared `workers` table, and a real person's YES could claim a task nobody paid for. Agents, judges and Manufact's harness need a server where quote_task, ask_eyes and await_answer return a verified answer with no key, without touching real workers or money.

## What
- `apps/mcp/src/main.ts`: `EYES_SANDBOX=1` builds the service with `createSandboxService`. It refuses to start with `EYES_PROVIDERS=live` or any `EYES_FAKE_WEBHOOKS`, and the error says why.
- `apps/mcp/src/sandbox.ts` (new), using only existing service methods:
  - `createSandboxService` wraps the fake messaging provider the engine is built with. An offer to a worker is answered YES at once, and 5 seconds after the capture link arrives the worker submits a capture at the task's coordinates with a fresh `captured_at`, an answer text that starts "Simulated sandbox answer, nobody went:" and a 12-byte JPEG header; fake vision passes it, so the task reaches `verified`. `quote_task` and `ask_eyes` join a worker with a fictional `+1 NPA 555 01XX` number at the resolved location and text START when the quote shows no free worker. `ask_eyes` runs one at a time, so each YES claims the task it was just offered. `ask_eyes` and `await_answer` `next_step` start with the sandbox sentence.
  - `keylessAgents` gives a request with no `Authorization` header an agent keyed on the caller's address (one hour after its last request, at most 10,000 addresses, at most 30 new agents a minute), made by `signupAgent` plus `updateSpendPolicy` (daily cap 1,000 USD), and topped up with 1,000 USD of play money whenever its balance is under 100 USD.
- `apps/mcp/src/server.ts`: in sandbox mode only, the bearer middleware asks `keylessAgents` when the `Authorization` header is absent; any header still goes through `authenticate`. HOME and `/status` show "Sandbox: keyless, simulated worker, no real people or money." with how to call it and drop the "no task gets answered" texting line; the server description, MCP instructions and `ask_eyes` description start with that sentence.
- `.env.example` lists `EYES_SANDBOX`; `docs/DEPLOY.md` says how the sandbox server is configured and deployed.

## Decisions & alternatives rejected
See [ADR-023](decisions/ADR-023-keyless-sandbox.md). In short:
- An agent per caller address, not per MCP session: mcp-use 2.10 is stateless and issues no session id (checked with a probe: no `mcp-session-id` on any response). Callers behind one address, such as everything coming from Manufact, share one agent, so its daily cap is raised to 1,000 USD and its balance is topped up; the daily cap remains the per-address limit.
- Keyless only in a separate server with its own database, never a flag on the live one.
- YES at dispatch inside a serial `ask_eyes`, not after a delay: a delayed YES claims the worker's newest offer, which can belong to a parallel task. Without the queue, three parallel asks at one place failed with `no_workers_nearby` in 4 of 4 runs.
- Free workers are reused instead of one new worker per task.

## Assumptions
- One sandbox server instance: the ask queue, the keyless map and pending captures are per process.
- Manufact forwards the caller address as the right-most `X-Forwarded-For` entry, as the signup throttle already assumes.
- The sandbox deploy does not set `ANTHROPIC_API_KEY`, `INKBOX_*`, `STRIPE_*` or `PRIMITIVE_*`.
