## Why
TestFlight's public link only works after Beta App Review. Ad hoc builds install from a link on iPhones registered in the Apple developer account, so workers can get the app now.

## What
- `/install#c=<code>` (worker web): the page trades the code (sent as a header, never in a URL) for a 1-hour profile link (`POST /w/device`). Step 1 downloads an iOS Profile Service profile; installing it posts the iPhone's UDID, model and iOS build to `POST /w/device/<ticket>`, which stores it in `worker_devices` and redirects (301) back to `/install?registered=1`. Step 2 (once the device is in an uploaded build) is the `itms-services://` install link, then the Developer Mode steps.
- `pnpm adhoc:release [--dry-run]`: registers new UDIDs with Apple (App Store Connect API key), builds and exports an ad hoc `.ipa` of `apps/mobile`, checks every registered UDID is in the embedded profile, uploads the `.ipa` and `manifest.plist` to the public InsForge bucket `apps`, and texts each newly included worker "Eyes is ready: tap to install https://app.eyes.pictures/install". `--dry-run` builds and checks only.
- The API serves the build (`GET /w/app/manifest.plist`, `GET /w/app/Eyes.ipa`) from the `apps` bucket without a redirect, so the itms-services install doesn't depend on iOS following storage's redirect to its CDN; the manifest's .ipa URL carries storage's `?v=` so each build is a new URL.
- STOP deletes the worker's devices (`eyes_set_worker_opt_in`). The privacy page says what a UDID is and why it is kept.
- Releases run without the operator's Mac: the public repo `i098/eyes-ios-release` (public so Actions minutes are free) has a GitHub Actions workflow that checks out `ayaangazali/eyes` and runs `pnpm adhoc:release` on a macOS runner. Every 5 minutes a Linux job counts unreleased devices and starts the macOS build only when there are any, so a registered iPhone gets its text in about 15 minutes; `/install` says "usually within 15 minutes". The repo variable `DRY_RUN=true` makes every run a dry run (for end-to-end tests). By hand: `gh workflow run release.yml -R i098/eyes-ios-release -f dry_run=true`.
- The API can also start the workflow at once with a `repository_dispatch` (`device-registered`, payload `ref` = `EYES_COMMIT` when set) after storing a UDID, if `EYES_RELEASE_DISPATCH_TOKEN` is set; a failed dispatch only logs, registration still redirects. Unset in production: creating the fine-grained token needs GitHub sudo (passkey) in a browser, and the 5-minute check makes it unnecessary.
- The archive is unsigned (`CODE_SIGNING_ALLOWED=NO`); the export signs it with the Apple Distribution certificate, so no development certificate is needed (the team is at Apple's development-certificate limit).

## Decisions & alternatives rejected
- The worker code never goes in a URL: the profile link carries a signed 1-hour ticket (`d:<worker id>`) instead of `?c=<code>`.
- Unsigned profile: iOS shows "Unverified". Signing needs a CMS signature with a trusted certificate; skipped until it costs sign-ups.
- Developer Mode is required on iOS 16+ for ad hoc builds; "Trust" in VPN & Device Management is not (that is for enterprise builds).
- Apple allows 100 iPhones per membership year; a STOPped worker's device stays on Apple's list until the year resets.
- Signing on the runner: an Apple Distribution certificate created through the App Store Connect API from an openssl key (never exported from a Mac keychain), loaded into a temporary keychain per run. Repo secrets: `DIST_P12`, `P12_PASSWORD`, `ASC_P8`, `RELEASE_ENV` (InsForge, Inkbox, ASC key and issuer ids). The repo lives on `i098` because that account cannot set secrets on `ayaangazali/eyes`.
