## Why
Workers are the "eyes": they need a page to sign up (and text START, without which Inkbox cannot text them, ADR-004) and a page that takes a live photo plus GPS at the place, so the engine can verify a fresh, on-site answer before paying out.

## What
- `@eyes/web-worker`: Vite 8.3.4 multi-page app, vanilla TypeScript, one CSS file. API base from `VITE_EYES_API_URL`; dispatcher number from `VITE_INKBOX_NUMBER` (substituted into `index.html` at build time).
- `index.html` + `src/join.ts`: name, phone (normalized to E.164, US default), "Use my location", `POST /w/join`. Success shows step 1 tap-to-SMS "Text START to <number>", step 2 "Set up payouts" to the returned `connect_url` (our `/w/connect/:token` redirect; hidden if null), and what to expect.
- `capture.html?t=<token>` + `src/capture.ts`: `GET /w/offers/:token`, question, place with map link, bounty, live countdown. Stops with a reason unless `status === "claimed" && claimed_by_you`. Live `getUserMedia` preview + canvas JPEG shutter; file input with `capture="environment"` only when getUserMedia is missing. "Do not photograph faces" note. `watchPosition` (high accuracy, stops at <= 50 m or 15 s, keeps the best fix), distance to the place. Yes/no for `is_open`/`in_stock`, optional text. Multipart `POST /w/offers/:token/capture` with `photo`, `lat`, `lng`, `accuracy_m`, `captured_at` (shutter time), `answer_text`, `answer_bool`; renders `CaptureResult` checks or the catalog error.
- `src/api.ts`: fetch wrapper that turns catalog error bodies into `message` + `fix` shown inline.

## Decisions & alternatives rejected
- GPS is re-acquired at every shutter press, not only on page load: a worker who opens the link on receipt and then walks over would otherwise submit the stale, far-away fix and fail `gps_ok`.
- Fallback file input sends `captured_at` from the file's `lastModified`, so a gallery photo fails the server freshness check instead of looking fresh.
- `@eyes/core` is imported type-only (erased at build, bundle has no zod); haversine is re-implemented in 5 lines because `@eyes/core/util.ts` imports `node:crypto` and the package exports only its index.
- All agent-supplied text is rendered with `textContent`, never `innerHTML`.
- Rejected: a UI framework, router or state library (two small pages).

## Assumptions
- The engine builds capture links as `{worker_web_url}/capture.html?t=<token>`; mcp-builder serves `/w/*` with CORS for the worker origin (cross-origin in production).
- Server maps `answer_text` "" and `answer_bool` "" to null when parsing `CaptureFields`.
- InsForge Sites builds via Vercel over HTTPS (docs/vendor/insforge.md), so camera and geolocation are allowed.

## Verification
- `pnpm exec playwright test --project worker`: 4 passed (join happy path asserts the posted body `{name, phone: "+14155550123", lat, lng}` and the `sms:` START link; join error shows message + fix; capture loads an offer, shoots from the fake camera, parses the multipart body and asserts a `photo` JPEG File plus lat/lng/accuracy/answer fields, renders the checks; invalid token shows the catalog error and no camera).
- Mutation checks, each made one spec fail: dropping the `photo` part, removing the GPS re-acquire at shutter, removing US phone normalization, ignoring catalog error bodies.
- `pnpm build`: Vite emits `dist/index.html`, `dist/capture.html`, about 9 kB of JS+CSS total.
- `pnpm verify:fast`: pass. Live-verified: no (needs deployed API and a phone).

## Known gaps
- Deploy (T2.3): build from the repo root so pnpm resolves the `workspace:*` devDependency and the lockfile.
- No retry UI for a denied camera permission beyond the inline fix text.
