## Why
An agent that loses a task_id (context reset, crash) had no way to find its open tasks, so it asked again and paid twice. The AX eval also found `quote_task` saying `allowed: true` for a question `ask_eyes` then refused: quote never sees the question, and its description claimed a spend-policy check the engine never ran.

## What
- `list_tasks({status?, limit=20})`: the calling agent's tasks newest first, max 50, with `answered` and a `next_step` that says resume with `await_answer` / `get_task` before `ask_eyes`. MCP tool, `GET /v1/tasks?status=&limit=`, `eyes tasks [--status] [--limit]`.
- `008_list_tasks.sql`: `eyes_list_tasks(agent_id, status, limit)`, `setof tasks`, filtered on `agent_id`, EXECUTE revoked from public/anon/authenticated.
- `quote_task` description, `allowed` and `reason_if_not` docs: `allowed` covers the place and task type only; `ask_eyes` checks the question; spend policy and balance come from `get_spend_policy` / `get_balance`. Behaviour unchanged.
- Docs regenerated: `llms-full.txt`, `openapi.json` (query parameters for GET routes), agent card; `llms.txt` and `agents.md` mention recovery with `list_tasks`.

## Decisions & alternatives rejected
- `answered` reuses the engine's `ANSWERED` statuses so it agrees with `await_answer`.
- The RPC returns whole task rows and the engine maps them, like `eyes_cancel_task`; no new index, since `unique (agent_id, idempotency_key)` already serves the `agent_id` filter.
- The REST route turns `limit` into a number before the strict schema parses it, so MCP input stays a real integer.
- Rejected: making `quote_task` check spend policy (behaviour change); cursor pagination (YAGNI at 50).

## Assumptions
- InsForge RPC returns `setof tasks` rows as a JSON array, as it already does for `eyes_cancel_task`.
