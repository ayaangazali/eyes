## Why
Issue #32: the live dashboard (map, task timeline, money ledger) only ran on the presenter's laptop with database credentials, bound to loopback because it shows worker locations. The demo depended on one machine, and judges could not open it.

## What
- `EYES_OPS_KEY` set (32+ chars): the deployed API serves the existing dashboard page at `GET /ops/<key>` and its feed at `GET /ops/<key>/feed`. Unset or empty: the routes are not mounted, so `/ops/...` gets the same unknown-route 404 as any other path. A wrong key gets that same 404 and never reads the feed.
- The key is compared as SHA-256 digests with `timingSafeEqual` (the inkbox webhook pattern), so length and content do not leak through timing.
- Headers on both routes: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and a CSP in the owner pages' shape (`default-src 'none'`, `base-uri 'none'`, `form-action 'none'`, `frame-ancestors 'none'`) that allows what the page needs: Leaflet from unpkg, its one inline script by SHA-256 hash (computed from the page at startup, so editing the script cannot silently break or widen it), map tiles and photos over `https:`, and `connect-src 'self'` for the feed.
- `main.ts` refuses to start when `EYES_OPS_KEY` is set but shorter than 32 characters, like `EYES_LINK_SECRET`.
- Reuse, not a fork: `apps/web/dashboard` exports `PAGE` and `readFeed(rpc)` (the `eyes_dashboard_feed` call and its limit). `@eyes/mcp` depends on `@eyes/web-dashboard`; `main.ts` passes `createRpc(db)` to `createServer` as an optional `rpc`.
- The page fetches its feed from `<its own path>/feed` instead of `/feed`, so one HTML file works at `/` locally and at `/ops/<key>` deployed. The loopback server is otherwise unchanged.

## Decisions & alternatives rejected
- Capability path `/ops/<key>`, the ADR-011 and ADR-020 link style: one URL the presenter opens and can hand a judge directly, no state, no form, no cookie. Our request log records unknown paths as `<other>`, so the key is never logged; `no-referrer` keeps it out of the Referer sent to unpkg and the tile server.
- Rejected: a one-time form that sets a cookie. It keeps the key out of the address bar, but needs a form page, a POST route and cookie handling, and a judge would have to be told the key and type it.
- Rejected: a public read-only view with coarsened worker positions. It invents a second feed and still exposes the timeline and ledger to anyone.
- Ops routes are deliberately not in `HTTP_ROUTES` (frozen agent contract) nor in llms.txt or openapi.json: they are an operator surface, not something agents call.
- `rpc` is optional on `createServer` so e2e, cli and evals callers (not owned here) keep compiling; without it the ops routes are not mounted.

## Assumptions
- The Manufact gateway forwards `/ops/...` like it forwards `/owner/...` (the owner console already works on the deployed URL, DEMO.md).
- The gateway may log request paths, as it may for owner links today. The DEPLOY note says to change the key after judging.

## Verification
- `apps/mcp/src/server.test.ts` "ops dashboard", 4 tests: unset and empty `EYES_OPS_KEY` (as in .env.example) give the unknown-route 404 on both paths, for the real key and an empty one, with no feed read; wrong keys (one char short, one extra char, upper-cased, `x`) give the same 404 with no feed read; the right key serves exactly the dashboard's `PAGE` as HTML and the feed row as JSON from one `eyes_dashboard_feed` call with `p_limit: 50`, both with `no-store` and `no-referrer`, and the page's CSP equals the expected policy built from the hash of every inline script in the served body (so a second inline script fails it).
- `apps/mcp/src/http.test.ts`: over a real socket, the right key's page and feed answer 200 and a wrong key 404, and the request log has exactly three `GET <other> <status>` lines, none containing the key.
- `apps/mcp/src/main.test.ts`: `EYES_OPS_KEY=demo` exits 1 with the 32-character message before listening.
- Old code fails the new tests: with origin/main's `apps/mcp/src/server.ts` and `main.ts`, 3 of the 6 new tests fail (right key, request log, short key); the unset and wrong-key tests pass there by design, since they assert nothing is exposed. Mutant `operator` accepting any non-empty key fails the wrong-key test. Mounting the routes with an empty key when `EYES_OPS_KEY` is unset is not reachable over HTTP (the router does not match an empty `:key`), so that guard has no observable mutant.
- `apps/web/dashboard/src/server.test.ts`: the page assertion checked the old `fetch("/feed"` source text; it now checks the page title. All local dashboard tests pass unchanged otherwise.
- Real browser (headless Chromium from @playwright/test, fake feed with a claimed task and 3 workers, through `toNodeListener`): at 1280 and 390 px the page at `/ops/<key>` loaded Leaflet under the CSP, polled `/ops/<key>/feed`, showed "Live", the task headline, 4 map markers and the tiles, with no console errors and no CSP violations; no request carried a Referer with the key. The same URL on origin/main answers the unknown-route 404. Screenshots are linked in the PR.
- `pnpm verify:fast` pass (unit 508, contract 11, safety 139, intent ok). `DATABASE_URL=.../eyes_t419 pnpm test:integration` 91/91 on a fresh database. live-verified: no.

- Verifier: security/privacy+spec+test+intent **PASS** ([verdicts/T4.19-PR67.md](verdicts/T4.19-PR67.md)): off and wrong-key look identical (404, no feed read, same timing); key in 0 logs, 0 HTML/JSON bodies, no Referer to tiles or CDNs; loopback dashboard unchanged.

## Known gaps
- Revoking a shared link means setting a new `EYES_OPS_KEY` and restarting the deployment; there is no per-viewer link.
- The address bar shows the key, so the presenter goes full screen (DEMO.md).
- A 32+ character low-entropy EYES_OPS_KEY (all spaces, one repeated character) is accepted; DEPLOY.md says to use `openssl rand -hex 32` (PR #67 minor).
