## Why
The first `pnpm ax:eval` run with `ANTHROPIC_API_KEY` (client A, claude-haiku-5-5) failed `surfaced_answer` on 2 of 3 tasks, though both final replies gave the user the answer and its verification:
- line: "Yes, the line is short right now: about 4 people, according to a verified answer ... The photo link points to a `storage.fake.test` address, which looks like a test or placeholder host, so I can't confirm the photo itself." The eval's fake storage host made Claude, correctly, decline to pass the link on as a real photo. The grader required the exact `photo_url` in the text.
- budget: the reply had the `photo_url` and "The answer passed GPS, freshness and photo checks, with 0.95 confidence", but not the substring "verif".
Both are the behaviour we want from an agent; the grader was matching one wording.

## What
`surfaced_answer` still needs an answered `await_answer` and its exact `photo_url` in the final text; the verification half now accepts "checked" as well as "verified" (`/verif|check/i`). New cases: the real budget reply (passes) and a reply that mentions a verified photo without its URL (fails).

## Decisions & alternatives rejected
- No LLM judge: a deterministic grader keeps the scripted client and CI cheap and repeatable.
- Not changing the eval's fake storage host to a real-looking one: that would teach the eval to reward an agent that relays a placeholder link as a real photo.
- The existing failing cases still fail: no photo_url ("Short line. Verified on site."), no verification ("Short line. Photo: <url>"), no answered await.
- Not accepting a reply that mentions the photo without its URL (round 1 of this PR did): the verifier showed ten replies that never relay the answer ("No photo yet, I'll check back later", "Done! Check the dashboard for the photo.") would pass, and the URL branch became dead code because every photo_url contains "/photos/". The URL is the only part of the check tied to the actual answer, and the tool text tells agents to show the user the photo_url (`apps/mcp/src/server.ts:359`).

## Known gaps
- The line reply that declined to relay the eval's placeholder `storage.fake.test` link still fails `surfaced_answer`. That happened once; in the rerun both Claude replies included the URL. It is an artifact of fake storage in the eval, not of live storage URLs.

## Assumptions
- The CI `ax:eval` job has no `ANTHROPIC_API_KEY`, so CI keeps running only the scripted client (`.github/workflows/ci.yml` integration job). Client A runs locally.
