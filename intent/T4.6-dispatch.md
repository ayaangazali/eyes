## Why
The UX audit found that a worker who already held a claimed task still got new offers, and a bare YES claims the most recent open offer. A late YES meant for the task they were working on claimed a task they never read. A worker's YES has to claim the task they actually read, and a worker holding a task should not get offers in the meantime. The offer text also gave no deadline and no way to opt out.
## What
- `006_dispatch_idle_workers.sql` replaces `eyes_nearby_workers`: a worker with a task in `claimed` or `submitted` is never returned, so they get no offer and are not counted in `quote_task.workers_nearby`. They come back once that task settles.
- It also replaces `eyes_claim`. A worker holding an unexpired `claimed` task gets `already_yours` for that task (the capture link is sent again) instead of claiming another open offer. Otherwise unchanged: the most recent offer whose task is `dispatched` and before its deadline wins, and settled tasks are never claimed. The worker check now locks the worker row (`for update`), so two YES from one phone run one after the other. The "lost" lookup drops its now-unreachable "mine" branch. Both functions get the PUBLIC/anon/authenticated revokes again, as in 002/004.
- Offer text: `Eyes: $3 to check how long the line is at Blue Bottle Coffee (0.9 mi) by 12:30 PM PDT. Reply YES to claim, STOP to opt out.`
## Decisions & alternatives rejected
- Workers with an unanswered open offer still get new offers (coverage over ambiguity). If we skipped them, one ignored text would keep a worker out for up to 240 min. With the demo's 3 workers, a second `ask_eyes` while the first is still dispatched would fail with `no_workers_nearby`. The engine's adversarial tests also post several tasks to one worker (expiry, daily cap, racing keys). The cost: an idle worker with two open offers who sends a bare YES claims the newer one. The capture link names the place, so they see which task they got.
- Busy means status only, with no clock check: `eyes_nearby_workers` has no `p_now`, and adding one changes the signature the engine (another builder) calls. A claim past its deadline keeps the worker out until `expireOverdue` runs.
- Claim-side guard as well as the dispatch filter: `askEyes` reads nearby workers outside the `eyes_post_task` transaction, so a worker can claim between that read and the offer insert. Offers sent before 006 is deployed hit the same path. The guard covers both cases. The guard is a check followed by a separate select, and under READ COMMITTED each statement gets a fresh snapshot. A first YES that committed between the second YES's guard and its offer select let one worker hold two claims (PR #39 verifier). Locking the worker row closes that window, and it is the lock we want anyway: claims for one worker are serialised, while different workers still race only on the task row. No other function locks a task and then a worker, so the lock order cannot deadlock.
- The deadline is absolute (`by 12:30 PM PDT`, the same `localTime` as the capture link) rather than "within 30 min". The text is often read late, which is exactly the case here, and a relative window goes stale and would need a clock in a pure template. `(0.9 mi)` replaces `, 0.9 mi away,` so the worst case ($49.99, the longest phrase, a 40-char place, 24854.8 mi) is 157 chars, within 159.
## Assumptions
- `create or replace function` keeps the owner and ACL (Postgres docs); the revokes are repeated anyway. `scripts/insforge-migrate.ts` picks up 006 by filename. No code sets `submitted` today (`eyes_submit` goes `claimed` to `verified` or `needs_review`); it is included per the task card.
## Verification
- `packages/db/src/dispatch.int.test.ts` (4 tests; the first 3 go through the same RPC path the engine uses): a worker holding a claim is not returned by nearby dispatch and is returned again after the task settles. A YES after their first task settled claims nothing and leaves the second task `dispatched`. A busy worker whose offer arrived in the dispatch race gets `already_yours` for their own task. The fourth test forces the race deterministically. It copies the live `eyes_claim` as `eyes_claim_paused`, which waits on an advisory lock between the guard and the offer select. A worker has two open offers, and the first YES claims inside an open transaction. The test waits until the paused second YES is blocked, commits, then releases the advisory lock. Result: `won` then `already_yours` for the same task, and the older task stays `dispatched`. The copy is dropped afterwards.
- Reverted to prove it: without 006 all 3 fail (nearby returned both workers; YES returned `won` for the second task). Removing only the nearby filter fails tests 1-2; removing only the claim guard fails test 3. Without the worker row lock, test 4 fails: the second YES returns `won` for the older task, so the worker holds two claims.
- `packages/comms/src/inkbox.test.ts`: exact offer text in PDT and PST, and the longest offer for every task type is within 159 chars and ends with the window and opt-out. These fail on the old template.
- `DATABASE_URL=postgres://postgres:eyes@127.0.0.1:54329/eyes_t46 pnpm test:integration`, rebased on main with 005 in the tree: 5 files, 51 passed on a fresh database (001-006 applied), then 51 passed again on the same one (engine and adversarial suites unchanged).
- `has_function_privilege('public', ...)` is false for both functions after migrate. After granting execute to `anon`, the 006 revoke block takes it away again (rolled back).
- When nothing is claimable, the engine's `claim()` sends "There is no open task for you right now..." (no silence). This is covered by the unchanged adversarial test "a YES after deadline_at but before expiry runs is not claimed".
- `pnpm verify:fast`: pass. Verifier (PR #39): PASS with two minors, both fixed in this round (the claim race above, and the rebase onto #35 with a regenerated INDEX).
- Verifier: spec+test+security+intent **PASS** ([verdicts/T4.6-PR39.md](verdicts/T4.6-PR39.md)): original bug reproduced on 001-004 and gone with 006 in both apply orders; 20-rep concurrency races clean. Its one race minor (check-then-act in eyes_claim) was fixed in the follow-up round with a worker row lock and a deterministic advisory-lock test; orchestrator reviewed the lock on 8a445cb.

## Known gaps
- A bare YES from an idle worker with two open offers still claims the newer one. Fix: a per-offer short code ("Reply YES A7"), which needs an engine change.
- An abandoned claim keeps that worker out of dispatch until its deadline passes and expiry runs, because claimed tasks cannot be cancelled.
- The busy check has no index on `tasks.claimed_by`; it filters through `tasks_status_deadline`, which is fine at demo scale.
