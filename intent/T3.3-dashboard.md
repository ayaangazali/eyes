## Why
During the demo (§13) the room watches the big screen while Claude asks. It has to show the pin and "3 workers notified" the moment `ask_eyes` returns, then the claim, the photo, the verification checks and the escrow turning into a payout, so judges see the human loop and the money path (Stripe track: escrow, release, refund) without reading logs.

## What
- `004_dashboard_feed.sql`: one read-only function `eyes_dashboard_feed(p_limit)` returning one row `{tasks, ledger, workers, totals}` as jsonb. Tasks carry status, money, times, `workers_notified` (offer count), the latest submission's photo and checks, and `money_at` (ledger type -> time). Workers carry only `id, lat, lng, available, opted_in`. Totals: escrowed now, released today, paid out today. EXECUTE revoked from PUBLIC and, when they exist, `anon` and `authenticated`; no table grants.
- `@eyes/web-dashboard`: `src/server.ts` (`node:http`, 127.0.0.1 only, `PORT` default 4400) serves `GET /` (`src/index.html`) and `GET /feed` through the `@eyes/db` rpc transport. DbConfig from `DATABASE_URL`, else `INSFORGE_BASE_URL` + `INSFORGE_API_KEY`. Run: `DATABASE_URL=... pnpm --filter @eyes/web-dashboard start`, open http://127.0.0.1:4400.
- `src/index.html`: plain HTML/CSS/JS. Left, a Leaflet map (task pins colored by status, sonar pulse while waiting or on the way, worker dots). Right, the newest active task as a narrated headline with a stepper (asked, N notified, claimed, photo, verified or needs review, paid; or expired/cancelled and refunded; disputed), the photo with GPS/fresh/vision checks and confidence, the money panel (three totals and the latest ledger rows), and earlier tasks as compact rows. Polls `/feed` every 2 s.

## Decisions & alternatives rejected
- No auth, by design: the dashboard runs only on the demo laptop. The bind address is hard-coded to 127.0.0.1 (no HOST knob), and requests whose Host header is not 127.0.0.1, localhost or [::1] get 403, so a DNS-rebinding page open in the same browser cannot read questions or worker locations.
- Function shape: multi-column `returns table` with one row, because single-column table functions serialize as bare scalars on both transports (T1.2 intent). `stable` SQL, so Postgres refuses any write inside it. `p_limit` caps tasks, ledger rows and workers (server passes 50).
- No phone or name ever leaves the database: the workers subquery selects five columns only. Worker coordinates are the JOIN location, acceptable on a loopback-only screen.
- "Today" is UTC midnight, matching `eyes_spent_today` and the daily cap. Escrowed now = escrow minus release, fee and refund over all tasks (the `eyes_agent_summary` formula across agents).
- `money_at` instead of deriving steps from status: a task disputed after payout still shows its payout step and time.
- Polling over InsForge Realtime: Realtime needs channel setup and anon access to `realtime.*`, while 2 s polling is the vendor note's documented fallback and works on both transports. The page re-renders only when the JSON text changes, and animates only steps and ledger rows that are new since the last render; all motion sits under `prefers-reduced-motion: no-preference`.
- No framework and no build: one HTML file read once at server start. Leaflet 1.9.4 from unpkg with SRI hashes (checked against the downloaded files). OSM tiles darkened with a CSS filter.
- Agent text (question, place label) is only ever set with `textContent`; the Leaflet tooltip gets a DOM node, never an HTML string.
- Money stays integer cents end to end (ADR-001). The browser divides by 100 only to format display strings with `Intl.NumberFormat`; `centsToUsd` cannot be imported into a no-build page.
- Map framing: the active tasks plus, per task, the nearest `workers_notified` online workers within 3000 m (the engine's dispatch rule with the `AppConfig` default), so the notified workers are in view; it flies to new tasks and fits on first load.
- Layout: newest active task first, money second, earlier tasks last as the only flexible row; a size container query hides the earlier list when it has no room, and short screens show four ledger rows instead of six.

## Assumptions
- InsForge (docs/vendor/insforge.md, UNVERIFIED like T1.2): `POST /api/database/rpc/eyes_dashboard_feed` with the admin key returns `[{tasks, ledger, workers, totals}]` and the admin role can EXECUTE the SECURITY INVOKER function.
- Photo URLs from the `photos` bucket load in a browser without auth. If not, the page hides the broken image and still shows the checks.
- unpkg and OpenStreetMap tiles are reachable at the venue; light demo use fits the OSM tile policy. Without Leaflet the timeline and money panel still work and the map pane says why it is empty.

## Verification
- `apps/web/dashboard/src/feed.int.test.ts` (Postgres): three opted-in workers and an agent through `createEyesService` with fake providers; after `askEyes` the feed shows `dispatched`, `workers_notified: 3` and escrow +350; after YES it shows `claimed` with `claimed_at`; after `submitCapture` it shows `paid`, the photo URL, gps/fresh/vision true, confidence 0.9, `money_at` keys escrow/fee/payout/release, ledger rows escrow 350, release 300, fee 50, payout 300, and totals deltas escrowed 0, released +300, paid out +300. Worker objects have exactly `available, id, lat, lng, opted_in`; the JSON contains no worker phone (E.164 or national digits), no worker name and no agent name. PUBLIC has no EXECUTE.

## Known gaps
- Not run against InsForge yet (needs keys, G2).
- Totals scan the whole ledger on every poll; fine for a demo-sized ledger.
- The engine never sets `submitted` (verification is synchronous), so the "Checking the photo" state does not appear today.
- Which workers were notified is inferred in the browser from the dispatch rule for map framing only; the feed does not expose offer worker ids.
- Only the newest 50 tasks and ledger rows are on screen.
