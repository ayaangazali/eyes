## Why
Agents spend from a prepaid balance that a human funds through Stripe Checkout, and workers are paid by a Transfer to their Connect account. This package is the only code that talks to Stripe: it turns verified webhooks into ledger credits and onboarding events, and serves the links humans click (`/topup/:token`, `/w/connect/:token`), so the judge sees funds in and funds out while escrow and refunds stay in our ledger.

## What
- `createStripePayments(env)`: Checkout top-up (mode payment, USD, one "Eyes balance top-up" line, `client_reference_id` and `metadata.agent_id`, also on the PaymentIntent so the charge is searchable by agent); worker Connect account; Account Link (`currently_due`); Transfer (`transfer_group` = task_id, `metadata.task_id`, caller's idempotency key); `parseWebhook` verified over the raw body.
- `stripeRoutes(deps, env)`: `POST /webhooks/stripe`, `GET /topup/done`, `GET /topup/cancel`, `GET /topup/:token` (clamped to 5..100 USD), `GET /w/connect/done`, `GET /w/connect/:token`. Explicit paths only; done pages registered before the `:token` routes.
- `scripts/fund-platform.ts`: confirms a PaymentIntent with `pm_card_bypassPending` so test transfers have available balance (ADR-004). Refuses to run when the API reports `livemode`.

## Decisions & alternatives rejected
- Connect account: Accounts v1 with `controller` (`fees.payer` and `losses.payments` = application, `stripe_dashboard.type` = express), US, `business_type` individual, `capabilities.transfers.requested`, idempotency key `eyes-worker-account-<worker_id>`, `metadata.worker_id`. This is the vendor note's recommendation; `type: "express"` is marked deprecated in the stripe 23.0.0 `.d.ts`; Accounts v2 can be blocked per merchant (`accounts_v2_access_blocked`). Fallback if the sandbox rejects v1: `stripe.v2.core.accounts.create` with `configuration.recipient` and `stripe_balance.stripe_transfers`, plus v2 account links (vendor note §4).
- Prefill only `individual.phone` and a fixed `business_profile.product_description`. Not the name: the JOIN name may be a nickname, and a wrong legal name is worse than an empty field.
- Optional `STRIPE_CONNECT_WEBHOOK_SECRET` beside `STRIPE_WEBHOOK_SECRET`: a Stripe endpoint gets platform events or connected-account events, never both (`WebhookEndpointCreateParams.connect`), each with its own secret. Workers' `account.updated` arrives on the Connect one, and the engine pays pending payouts on `worker.onboarded`, so one secret would silently strand them.
- `constructEventAsync`: same call as `constructEvent`, also works where only SubtleCrypto exists. Secrets are read per webhook, not at startup, because the dashboard secret exists only after the URL is deployed.
- Redirect errors render an escaped HTML page (`hono/html`) with the EyesError message, fix and status: these links are opened by humans. Bad signature: 400 with Stripe's message. Service errors reach Hono's handler as 500 so Stripe retries; `creditTopup` is idempotent on `stripe_ref`.

## Assumptions
- Param and field names (`payment_intent_data.metadata`, `idempotencyKey`, `collection_options.fields`, `capabilities.transfers`) come from the stripe 23.0.0 `.d.ts`, not a live call (docs/vendor/stripe.md Open questions).
- A US individual on the full service agreement can hold only the `transfers` capability. Sandbox keys accept `pm_card_bypassPending`.

## Verification
- `pnpm vitest run --project unit packages/payments`: 15 passed. Routes with `fakePayments` and a stub service: bad signature 400 with no service call; `topup.completed` credits exact cents with the session id as `stripe_ref`; `worker.onboarded`; unhandled event 200; service failure 500; top-up 302 with clamping (20, 500, 1, none -> 2000, 10000, 500, undefined); done pages never reach the token handlers; connect 302; EyesError renders as 404. Real adapter with events signed by `Stripe.webhooks.generateTestHeaderString`: paid session mapped, tampered body and missing signature rejected, unpaid ignored, Connect-signed `account.updated` mapped only when transfers are active or payouts enabled, other types null, missing key throws.
- Hand mutations, each failed a test: skipping verification, dropping the clamp, moving `/topup/done` after `:token`, ignoring `payment_status`, accepting bad signatures, dropping the Connect secret.
- `pnpm verify:fast`: pass. live-verified: no (no sandbox keys yet).

## Known gaps
- Request bodies sent to Stripe are checked by the type checker only; confirm on the first live run (T2.3).
- `checkout.session.async_payment_succeeded` is not handled; cards complete synchronously.
- Deploy needs two event destinations to `/webhooks/stripe`: "Your account" (`checkout.session.completed`) and "Connected accounts" (`account.updated`). Locally, `stripe listen --forward-to ... --forward-connect-to ...` uses one secret for both.
